- **Item-type identity alignment** (`feature/item-type-identity-alignment`) — Separated item-type *identity* (database) from *presentation* (config), the last refactor before Phase 0. The catalog is now keyed by the persisted natural name (`snippet`, `prompt`, …) and no longer carries hardcoded ids, which would have broken as soon as the seed assigned cuids; `toItemTypeViewModel()` joins a persisted `{id, name, icon, color}` row with the configured `{label, slug, contentType, isPro}` and validates the untyped persisted `icon` at that boundary. Renamed `ContentKind` → `ContentType` (`TEXT | FILE | URL`) to match the generated Prisma enum, and split the item `content` field — which had been doing triple duty as text body, link URL, and filename — into real `content` / `url` / `fileUrl` / `fileName` / `fileSize` columns. Made the mock records persistence-honest: opaque ids, `Date` timestamps serialized to ISO in view models, and nullable `description` / `defaultTypeId` / `User.name`. A nullable `defaultTypeId` means an empty collection can have no dominant type, so `CollectionViewModel.dominantItemType` is nullable and its card renders a neutral accent (an *unresolvable* type id still throws). Rewrote the `project-overview.md` data model to the course-aligned schema: `contentType` on `Item`, `defaultTypeId` as a real FK, NextAuth models, `User.password`/`emailVerified`, and `@@map` table names. Left unsolved and flagged for Phase 0: `@@unique([name, userId])` does not constrain system types, because Postgres treats `NULL`s as distinct — the course's `upsert` seed is not idempotent.
- **Prisma + Neon foundation** (`feature/prisma-neon-foundation`) — Roadmap Phase 0. Stood up Prisma 7.8 against a Neon Postgres dev branch: `schema.prisma` (the seven models, the `ContentType` enum, NextAuth's `Account`/`Session`/`VerificationToken`, indexes, cascade deletes), the `init` migration, a seed for the seven system item types, and the `src/lib/prisma.ts` singleton. Prisma 7's breaking changes drove most of the shape: driver adapters are now mandatory (`@prisma/adapter-pg` over Neon's pooled endpoint), `prisma.config.ts` replaces both the schema's datasource `url` and the `package.json` seed key, `.env` is no longer auto-loaded, the generator is `prisma-client` (not `prisma-client-js`) with a required `output` — so the client is generated to a gitignored `src/generated/prisma` and imported from there rather than `@prisma/client` — and `migrate dev` no longer runs the seed. Two connection strings: pooled `DATABASE_URL` for the client, direct `DIRECT_URL` for the CLI, since migrations take session locks PgBouncer cannot serve. **Closed the system-type uniqueness hole carried over from the last refactor, but not by the planned route.** Hand-writing `CREATE UNIQUE INDEX ... WHERE user_id IS NULL` into `migration.sql` is no longer viable: since 7.4 Prisma treats database objects absent from the schema as drift and emits a `DROP` for them on every `migrate dev` (prisma#29220, #29263). The index is instead declared in the schema through the `partialIndexes` preview feature — `@@unique([name], where: { userId: null })` — so Prisma owns and tracks it; a second `migrate dev` confirms no drift. Verified on the live database: re-seeding reports `0 created, 7 updated`, and a duplicate `('snippet', NULL)` is rejected with P2002. One wart to code around: that partial index makes Prisma leak `name` into `ItemTypeWhereUniqueInput` (prisma#29282), so `findUnique({ where: { name } })` type-checks even though `name` is unique only among *system* rows — always scope by owner with `findFirst({ where: { name, userId: null } })`. Added `scripts/test-db.ts` (`npm run db:test`) as a repeatable smoke test: it checks both Neon endpoints (the pooled and direct URLs fail independently — a broken `DIRECT_URL` looks fine until the next migration), the migration history, the seeded types, and the constraint itself, probing it inside a rolled-back transaction so a regression cannot leave a duplicate row behind. Production promotion is `npm run db:deploy` (`prisma migrate deploy`, which applies pending migrations without diffing or resetting) plus one `npm run db:seed` — never `db push`. The mock query layer in `src/server/mock-data/` is untouched and still backs the UI; swapping it for real Prisma reads is the next step.
