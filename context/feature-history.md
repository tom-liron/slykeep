24. **Email verification on registration** (`feature/email-verification`) — New credentials accounts are created unverified and cannot sign in until they click a single-use link, making `User.emailVerified` a signal the account-linking work can trust. Tokens are 32 random bytes stored as a SHA-256 digest, so a database read yields no working links; the unverified check sits *after* the bcrypt compare, where naming the account's state discloses nothing the caller has not already proven, and the decoy-hash timing guard survives intact. GitHub sign-ups are marked verified by a `linkAccount` event, since the provider's profile mapping leaves the column null and the ambiguity would make it useless. The whole feature was written, discarded, and rewritten: delivery fails at Resend, not in this code — every send from the account fails asynchronously with "Domain is not verified", including `onboarding@resend.dev` to Resend's own `delivered@resend.dev` simulator, with `POST /emails` returning 200 and a null error throughout. The first attempt hid that behind a console-printed link and so reached "done" without ever sending an email; this one keeps the workarounds in `scripts/` (`email:test` polls `last_event` until it settles, `user:verify` marks an account by hand) where they cannot make the product lie. Resend support confirmed the outage as their own defect and fixed it; `onboarding@resend.dev` now delivers, though only to the account owner's own address, so a verified domain is still required before real users can receive anything.
25. **Review follow-ups** (`fix/resend-timing-oracle`) — A review pass over the two unpushed auth features turned up one real defect. `POST /api/auth/verify-email` equalized its response *body* across every outcome but not its *timing*: only the unverified-credentials path issued a token and awaited a round trip to Resend, so latency alone separated those accounts from unknown, already-verified and OAuth-only addresses — the enumeration oracle `ABSENT_USER_HASH` exists to close, reopened one file over, in an endpoint whose own docstring claimed parity with it. 26. **Password reset** (`feature/password-reset`) — A "Forgot password?" link on the sign-in form and the flow behind it: `/forgot-password` asks for an address, a single-use link lands on `/reset-password`, and the new password is written by `POST /api/auth/reset-password`. Reset tokens live in the same `VerificationToken` table as the confirmation ones, which is the whole risk of the feature: that table has no purpose column and a token is found by its digest alone, so without a namespace a *verification* token posted to the reset route would let anyone who can receive that email set a password on the account. Both purposes now carry an explicit `identifier` prefix — including verification, which previously used the bare address, because a purpose defined as "no prefix" has to exclude every future purpose by name and the failure mode of forgetting is silent. The request endpoint answers 200 for everything with the lookup and send in `after()`, the same enumeration parity `POST /api/auth/verify-email` settled on; the reset endpoint is free to name its failures, since the caller is identified by a token they had to receive rather than an address anyone can type. Three smaller decisions: a reset link also sets `emailVerified` (receiving it is the same proof the confirmation email asks for) but never overwrites an existing timestamp; the token is checked before the bcrypt hash and consumed after, so junk input cannot buy 500ms of CPU on an unrated endpoint and a hashing failure cannot spend a live link; and `/reset-password` is reachable *with* a session, unlike the other signed-out routes, because a reset link is opened from whatever browser the mail client hands it to. An account with no password gets a "you sign in with GitHub" email instead of silence, which discloses nothing — it only ever reaches the address that was entered. Rate limiting is still missing, and JWT sessions still have no version claim, so a reset cannot evict a session held by whoever knew the old password.
27. **Honour the sign-in callback URL** (`fix/sign-in-callback-url`) — The proxy had been writing `?callbackUrl=` on every bounce and nothing ever read it: both sign-in paths hardcoded `redirectTo`, so a signed-out deep link to a collection always dumped you on the dashboard, and the most common bounce of all decorated the address bar with `?callbackUrl=%2F` for no benefit. Sign-in now returns you where you were headed. A Server Action cannot see the URL of the page that invoked it, so the value travels as a hidden field in both forms rather than being read from the request — which makes it exactly as forgeable as the query param, hence `resolveCallbackUrl` validating at both ends. It accepts same-origin relative paths only: absolute URLs, protocol-relative `//host`, and the `/\host` form browsers normalize into it are all refused, since honouring any of them is an open redirect that inherits the credibility of the site the user just trusted with a password. The auth pages are refused too, as returning to `/sign-in` after signing in is a loop. `welcome=back` stays on the default destination alone: `WelcomeToast` is rendered only by the dashboard home and clears its flag with a hardcoded `router.replace("/")`, so attaching it to a deep link would raise no toast, strand the param, and one day redirect people off the page they asked for. The proxy's route sets moved to `lib/auth-redirects.ts` because the guard needs the same list and two copies would drift.

32. **Recover from a session whose user no longer exists** (`fix/stale-session-user`) — A JWT outlives the row it names, and `getCurrentUser` threw when that row was gone: every page answered 500 with no way out of it, because the token still parses, so the proxy treats the visitor as signed in and redirects them off `/sign-in` back to `/`, which throws again. The render now redirects to `GET /api/auth/stale-session`, which clears the cookie and returns them to the sign-in form. It has to be a route handler rather than a `signOut()` where the problem is detected — server components may not write cookies, and the cookie is the one thing that ends the loop. The handler re-checks that the row really is missing before clearing anything, which is what makes it safe to expose: a `GET` that unconditionally signed people out would be logout CSRF, droppable by an `<img>` tag on any page. `SessionUserMissing` joins the codes in `lib/auth-errors.ts` so the form explains itself instead of inviting a retry that cannot work. `getProfile` keeps its throw — it fires only when the row disappears between two queries of one request, which is a genuine race and not a stale cookie. This is not session revocation: a live JWT for a *surviving* account is still untouchable, which remains the `sessionVersion` question deferred in §11. It only makes an already-fails-closed case fail closed gracefully.

33. **Rate limiting for auth** (`feature/rate-limiting-auth`) — Upstash Redis sliding windows on the five auth entry points, closing the gap Phase 1 deferred. The credentials limit lives in `authorize` rather than in the sign-in Server Action, because `POST /api/auth/callback/credentials` is public and a script driving it never touches the form — limiting the action would have protected the only caller that was never the threat; it throws a `CredentialsSignin` subclass like the unverified-email one, so the message reaches the form through the existing `code` path, at the cost of not being able to carry the remaining minutes. Sign-in and resend key on IP *and* email: per-IP alone locks out everyone behind one office NAT, per-email alone hands an attacker a way to lock a known address out of its own account. The other three key on IP alone, since mixing in the submitted address would hand a fresh budget to every address a script invents, which is the abuse itself. The two enumeration-safe routes now have one answer that differs, and it is safe — a 429 depends on the caller's own request count, never on whether an address exists — but both forms had to stop claiming a link was on its way for a request the server refused. Writing the fail-open test against a real transport showed fail-open was not working: the SDK retries five times with exponential backoff (~4.7s, so every sign-in stalled that long during an outage) and had no timeout at all, and a `catch` cannot fail open on a promise that never settles, so a hung Upstash would have hung sign-in indefinitely. Retries are pinned to one and checks bounded at a second. Two things left as they are, with the reasoning recorded in `rate-limit.ts`: the retry estimate is optimistic, because the SDK's `reset` is the next window boundary rather than when this caller regains capacity, and reporting the truth means reimplementing decay the library does not expose; and the module carries `import "server-only"` despite the spec naming a `lib/` path, since that directory is client-reachable and the REST token must not reach a browser bundle. Found but deliberately not fixed here: `ResendVerification` renders a `<form>` inside `SignInForm`'s `<form>`, which is invalid HTML, so its submit handler never runs and the resend control has never worked — pre-existing on `main` and tracked separately, which leaves the 429 path in that one component verified by inspection only.

34. **Resend control could never be clicked** (`fix/resend-nested-form`) — `ResendVerification` rendered a `<form>`, and its only caller renders it inside `SignInForm`'s `<form>`. Two consequences of the field now belonging to the sign-in form: it carries no `name`, or a second `email` entry would ride along with the credentials, and Enter is handled explicitly, or the key would resubmit the password that just failed. Verified in a browser end to end — no navigation, no hydration error, the 429 rendering below the row as intended, and Enter issuing the request rather than the sign-in.

38. **Item detail drawer** (`feature/item-drawer`) — Clicking an item card opens a right-side Sheet with the item's full detail; there is no separate item page. The drawer opens on the summary the card already carried and fetches only what a list query never selects — the body, the collections holding it, the creation date — so the title, type, tags, and description are on screen before the request is sent, and the skeleton covers three fields rather than the whole panel. `getItemDetail` puts ownership in the `where` rather than checking the result, which makes another user's id indistinguishable from a missing one; a test pins that by filtering the Prisma stand-in only on the keys actually present, so a refactor to `findUnique({ where: { id } })` fails that test instead of quietly serving someone else's item — verified by making the change and watching only that test break. `GET /api/items/[id]` is a route handler because the drawer distinguishes 404 from a retryable error, the same rule that made `api/auth/register` one. Two structural decisions came from constraints rather than taste: the trigger is an overlay button rather than the card itself, because a `<button>` may contain only phrasing content and `ItemCard` renders an `<article>` with a heading — the same invalid-markup class as the nested `<form>` that once left the resend control unclickable — which also leaves `ItemCard` untouched and still usable as plain markup; and the React Compiler's rule against synchronous `setState` in an effect ruled out clearing the fetch state there, so `ItemList` keys the drawer by item id instead and holds `open` separately from `selected`, which incidentally bought the close animation. The collection page was wired alongside the dashboard and item-type pages the spec named, since all three render the same card and one that looks identical but does not open reads as a bug rather than a smaller scope. 44. **File & image upload with Cloudflare R2** (`feature/file-image-upload`) — `file` and `image` join the creatable types: `FileUpload` drops or picks a file, `POST /api/upload` validates it and puts it in R2, and the create dialog submits the returned key with the rest of the form. The instructor's completed repo was inspected first and deliberately not followed. It stores the full public URL in the item row and renders images straight from a public bucket, so its download proxy — which re-fetches that same public URL server-side — authorizes nothing that the URL in the page does not already give away. Here the bucket is private and `GET /api/files/[id]` is the only way in: it looks the *item* up for the signed-in user and reads the key off that row, so a caller can only ever name an item and there is no path string for a `..` segment to defeat. `Item.fileUrl` was renamed to `fileKey` by a hand-written `ALTER TABLE … RENAME COLUMN`, because Prisma generated a drop-and-add that is only equivalent while every value is NULL, and the column now holds `users/<id>/<uuid>` rather than a URL — which keeps a later move to presigned URLs a route change instead of a data migration, and keeps deletion from having to parse a key back out of a URL as the course's does. Validation is extension-first with the media type checked only when the browser supplied one, because `File.type` is empty for `.md` and `.toml` on most platforms and refusing that would refuse ordinary uploads. Deletion removes the object *after* the row commits and swallows the failure: an orphan nobody can see is a cheaper mistake than an item pointing at nothing. Previews went past the spec on purpose — nine of the ten allowed formats are text, and the renderers already existed, so markdown opens as a note does, the rest highlight in Monaco, PDFs go to the browser's viewer with `#toolbar=0`, and Copy now works on a stashed `.env.example`; SVG is never served inline and previews as its own source instead, and the route gained `X-Content-Type-Options: nosniff`, which only matters once responses are rendered rather than downloaded. Replacing a file is deliberately absent: it is the one mutation with an ordering hazard, and the edit form shows the object read-only instead. The session's real lesson was a CSS one: the drawer had been **384px wide** on every viewport at or above `sm`, because `SheetContent`'s own `data-[side=right]:sm:max-w-sm` out-specifies any `sm:max-w-*` passed in and `cn` cannot merge the two — which is why five labelled toolbar buttons overflowed and put a horizontal scrollbar under file items but not commands ("Download" is wider than "Copy"). Three confident wrong diagnoses preceded finding it. The width is now set on the same variant so the defaults are dropped rather than fought, sized from the floor the toolbar needs, and the labels collapse to icons below `sm`. R2 itself was verified end to end with a throwaway put/get/delete against the real bucket; the HTTP path was checked by hand in the browser.

48. **Link scheme validation and upload rate limiting** (`feature/link-scheme-and-upload-limits`) — Two hardening fixes from a codebase audit, both closing a gap where an existing control stopped one step short. `optionalUrl` used `z.url()`, which validates *shape* and not scheme — probed against the installed Zod 4.4.3, it accepted `javascript:`, `data:`, `vbscript:` and `file:` as readily as `https:` — while `ItemDrawer` renders the stored value as an `href`, so a saved `javascript:` URL ran on this origin when the link was clicked, through both the create and the edit path since both share the field. Bounded with `protocol: /^https?$/` and pinned by tests over all four schemes plus the two that must still work in any case. Only the owner can open their own item's drawer, so this was self-inflicted today; it was fixed anyway because it costs one regular expression and stops being self-inflicted the moment an item is shared or exported. `POST /api/upload` gained the limiter the four auth routes have had since `feature/rate-limiting-auth`: 30 in 10 minutes, checked before the body is read so a refused caller cannot stream 10 MB in first. It is keyed on the **account**, not the IP — the route is behind the session, so the better identifier is available, and an IP would bill one office NAT for everyone behind it — which meant `checkRateLimit`'s second parameter stopped being an IP and was renamed `caller`, with `keyBy` gaining a `"user"` case. This route rather than every mutation because it is the only one that writes to paid storage, accepts 10 MB a request, and stores the object *before* the item row exists, so a loop that never finishes creating an item leaves orphans nothing points at. Three other candidates were checked against the code and rejected rather than built: bcrypt rounds are already 12 and are not a free number to change, since `ABSENT_USER_HASH` is a decoy precomputed at that cost to equalize sign-in timing; there is nothing to debounce yet, because every `onChange` in the item forms and both editors sets local state and `MarkdownEditor`'s Preview unmounts while Write is active, which makes it a Phase 3 concern arriving with search; and `next/image` would *break* two of its three candidate call sites, since `FilePreview` and `ImageCard` read `/api/files/[id]`, an authorized route whose optimizer fetch would arrive without the session cookie. That last one is the downstream consequence of the private-bucket decision — the course's public bucket is exactly why the same swap works there — and the reasoning already lives in `r2.ts` and beside both `<img>` tags. The dev database was checked for rows the new rule would retroactively invalidate: 7 URLs, none of them non-`http(s)`, so no migration.

That ranking lives in `lib/fuzzy-search.ts` as pure functions: tiered — exact, prefix, word start, substring, scattered — with a coverage bonus that only ever reorders inside a tier. The first version was too loose in exactly one place, and the fix is most of what this entry is about: subsequence matching over prose is barely a filter, since the letters of "test" are hiding in order inside almost any sentence, which is how a search for it returned half the library. Scattered matching is now opt-in per field (titles, tags, and collection names only — descriptions and type labels need a real occurrence), needs at least four characters, and may interleave at most two characters total. That allowance is flat rather than a ratio on purpose: a ratio grows the slack for precisely the short queries that need reining in. Item bodies are still never read, so full-content search stays a server-side question for later. The top bar became three flex tracks so the field sits on the middle of the page rather than wherever the brand and toggles happen to end, and the shadcn `Command` component was adapted rather than installed — its `radix-nova` variant depends on `input-group` and a docs-app icon shim, and its installer wanted to overwrite `button.tsx`, so `cmdk` is the only new dependency. The palette owns its trigger and open state, like the two create dialogs beside it, which is also what keeps the query reset out of an effect the compiler's `set-state-in-effect` rule rightly rejects. Ownership scoping on both reads is unit-tested for the reason it matters here: the data is prefetched and matched in the browser, so the `where` *is* the access control.

55. **Pagination** (`feature/pagination`) — the item type pages, the collections grid, and a collection's own page now render 21 rows at a time under numbered page links, and the queries behind them read one page instead of everything. Page sizes live in `config/pagination.ts`; the two dashboard caps the spec bundled with them went to `config/dashboard.ts` instead, because they bound a summary list that has no page 2 rather than a window. `lib/pagination.ts` holds the pure parts — a `?page=` that is missing, fractional, negative, or a word all resolve to page 1 rather than 404ing a link somebody shared, and the requested page is clamped against the real total *before* it becomes a `skip`, which is why every query counts first rather than counting in parallel: `?page=99` would otherwise answer with an empty grid under controls claiming there was something there. Each paginated `orderBy` gained `id` as a tiebreaker, since `skip`/`take` only means anything over a total order and items written together share an `updatedAt` — without it Postgres may return them either way round, which is how one row appears on two pages. The collection page is where the read actually changed: it had been pulling every item at full summary width through the collection's join, so it was split in two — the collection row keeps the two-scalar item join that the header's count, dominant type, and type breakdown are all derived from (those describe the whole collection, not the page) and the items are a separate `skip`/`take` query, with the total taken from the join's length rather than a second `count`. The old `ITEM_TYPE_PAGE_LIMIT = 200` safety valve is gone, and the item type header now prints the pagination's `totalCount` rather than the length of what it is showing. Prev and next render as a `<span>` when there is nowhere to go rather than a greyed `<Link>`: a link that only looks disabled is still clickable, focusable, and announced as a link. Page 1 links to the bare path, so a listing's canonical URL never carries a param meaning "default".

60. **Favorites page sorting** (`feature/favorites-sorting`) — `/favorites` can now be ordered by name, date, or item type, in either direction, without a round trip: the rows are already on the client and both lists are only as long as one person's stars, so re-`ORDER BY`ing them in Postgres would cost a read per click to answer a question already in memory. One control drives both sections, because the two are deliberately one list with a heading in the middle. The rule lives in `lib/favorites-sort.ts` as pure functions, and the shape it compares is the point: an item has a `title` and always has a type, a collection has a `name` and may have none, so the house `sortByUpdatedAtDesc<T extends { updatedAt }>` idiom does not reach — each shape projects to a four-field `FavoriteSortFields` and only the comparator sees it, which also means its nineteen tests need no view-model fixtures. Three details carry the whole thing and each looks like a nit. The tiebreak (`updatedAt desc`, then `id desc`, matching what the server already returns) is applied *outside* the direction flip, or toggling the arrow would reshuffle every equal-named row — jitter that is harder to notice than the reordering the user asked for. The missing-type branch is answered *before* the flip too, so collections with no dominant type sink in both directions rather than quietly surfacing at the top of a descending sort; labelling them "No type" and sorting that string was rejected as inventing a type that does not exist. And `updatedAt` is compared as a string, since both view models build it with `toISOString()`, which makes lexicographic order chronological and the result identical to the query's rather than merely equivalent. Changing the key resets the direction to that key's own default — dates want newest first, names want A–Z — because carrying it across lands on Z–A and reads as broken. The control is a `DropdownMenu` radio group plus a direction button; there is no `select.tsx` in `components/ui` and one sort control is not a reason to add one. Where it sits took four passes and the last one moved code: on the page heading's line it read as chrome belonging to the title, a long way above the rows it reorders, so it ended up in the first section's heading row via an `action` slot on `SectionHeading` — bottom-aligned, since the row's height comes from the button and centring leaves the small uppercase label floating in the middle of it. That puts it inside one `<section>` while it governs both, a semantic fib named in the code rather than papered over; the alternative, one control per section, is what the single-list design rules out. The heading and the empty state moved into the client component with it, so there is one `<h1>` rather than one per branch, and the page's subtitle went entirely — "most recently updated first" stopped being true the moment the order could change.

62. **Item.editedAt and the recency indexes** (`feature/item-edited-at-recency-indexes`) — `updatedAt` had quietly become four things at once: Prisma moves it on any write, so a content edit, a favourite toggle and a pin toggle were indistinguishable, and every "recent" surface ordered by it. Starring a year-old snippet lifted it to the top of the dashboard's Recent list; unpinning one dropped it back in at position one. `Item.editedAt` splits the edit out — written by hand in `updateItem`, taken from the column default on create, and touched by nothing else. It is deliberately not `@updatedAt`: being Prisma-managed is precisely what made `updatedAt` unusable here, and suppressing it on the toggles would have meant reading the row first, reopening the race both toggles were written to avoid. The finished course repo was inspected before deciding and offered nothing to copy — generic `updatedAt` from its init migration through its last commit, no dedicated timestamp ever added or removed, no fix commit touching an `orderBy`, and its "recently used items" bullet shipping as `updatedAt desc` — so the conflict there was never confronted rather than resolved. `favoritedAt`/`pinnedAt` were the first instinct and solve the wrong half: they improve the favourites ordering while leaving `updatedAt` still moving, so Recent stays polluted. Every item recency read moved — both dashboard lists, the type pages, a collection's items, `/favorites`, and the search prefetch, where the key is not cosmetic because the prefetch is capped and so decides which items are searchable at all. The read side is only half of it: four components render an item's date, and a list that sorts by one date while showing another looks broken, so the cards, the row, the image card and the drawer (whose *Updated* label became *Edited*) all render `editedAt`, and `updatedAt` came off `ItemSummaryViewModel` entirely — it has no UI reader left and is now a pure audit column. That is what forced `/favorites` onto `editedAt` too, giving up the "recently starred" ordering it had been getting by accident. Two renames followed from the split rather than being tidying: `FavoriteSortFields.updatedAt` became `sortDate`, since the two sides no longer date from the same column and a field named after either would lie about the other, and the dominant-type tiebreak moved to `editedAt` because "which tied type has the most recent item" is an item recency question — on `updatedAt`, favouriting an item could recolour a collection's accent. The migration backfills `editedAt` from `updatedAt` before building the index, or every existing row would collapse to the deploy timestamp and flatten the ordering the column exists to fix. It also carries five composite indexes the recency, favourite and pin queries had been running without — the one part of this the course does have, in an early audit commit we were simply behind on — and drops `items_createdAt_idx`, which nothing has ever ordered or filtered by.

63. **Pinned items in Recent, and a pinnedAt column** (`fix/pinned-items-in-recent`) — found by testing the previous entry: editing a pinned item changed nothing visible anywhere on the dashboard. 64. **SSL mode pinned to verify-full** (`fix/env-example-sslmode`) — the first page load after every dev server restart raised a "Console Error / Server" in Next.js's overlay, attributed to `DashboardLayout`, and a second refresh cleared it. It was `pg-connection-string` warning that `sslmode=require` will stop meaning `verify-full` in pg v9, emitted through `process.emitWarning` behind a module-level `warned` flag — once per Node process, so only the first request could ever see it, which is what made a config warning look like a page bug. 65. **Command palette crash on a keyless keydown** (`fix/command-palette-undefined-key`) — creating an item could take the page down with `Cannot read properties of undefined (reading 'toLowerCase')` from the ⌘K listener. The shortcut is registered on `window`, which is the right scope for a global shortcut and also means it receives every keydown on the page rather than only the ones our own components cause; an event dispatched as a plain `new Event("keydown")` satisfies the `KeyboardEvent` type at compile time while carrying no `key` at runtime, TypeScript typing the interface rather than what actually arrives on a listener anything may reach. The sender was never pinned down and the entry first claimed one anyway: nothing in `node_modules` dispatches a synthetic keydown, monaco was a guess written in the voice of a finding, and the only real evidence was a `content-script.js` frame in the console — a browser extension. Which is the argument for guarding the dereference rather than the sender, since the page's other occupants are not ours to fix. The guard tests the modifier first and reaches `key` through `?.`. It is the only `window` keydown listener in the codebase; the one other reader of `event.key` is a React handler on an element, where `!== "Enter"` on `undefined` is merely false rather than fatal. No test: the handler lives inside a `useEffect` and driving it needs `jsdom`, which the component tests here still do not use. The fix then appeared not to work, which turned out to be worth more than the fix. `event.key?.toLowerCase()` cannot throw on a missing `key` — optional chaining short-circuits the call — so what was still throwing was the *old* closure: the original crash tore the tree down without running the effect's cleanup, leaving a pre-fix listener bound to `window` while Fast Refresh mounted a second one beside it. The stack resolved through the file's current sourcemap and so pointed at the new line, showing code that provably could not have raised it. A hard reload drops every `window` listener; Fast Refresh does not.

70. **Mobile touch targets** (`feature/mobile-touch-targets`) — Branch 3 of the responsiveness effort: every control is at least 44px when the pointer is coarse, and unchanged when it is not. `button.tsx` sized every variant for a mouse — 24px at `icon-xs`, 28px at `icon-sm`, 32px at `icon` — against Apple's 44pt, Material's 48dp and WCAG 2.2 SC 2.5.5, and those sizes sit on exactly the surfaces a phone uses most. The condition is `pointer-coarse:`, not a width breakpoint, because a touch laptop at 1440px has the problem and a mouse at 390px does not; it also keeps the change off the desktop layouts branches 1 and 2 measured into place. Boxes grow rather than a `::after` extending the hit area past them: the top bar's controls sit on a `gap-2`, so 6px of invisible overhang per side would have each button overlapping its neighbour by 4px, and an invisible overlapping target is worse than a small one. The switch is the one exception, and grows its hit area instead — 20×36 is what reads as a switch, and each one is alone at the end of a `PanelRow`, so nothing is within reach of the overhang. Verification could not emulate a coarse pointer, so the harness lifts the real `(pointer: coarse)` rules out of the compiled stylesheet, re-emits them unconditionally, and probes each control with `elementFromPoint` at ±21px from centre in four directions — what a thumb reaches, including the pseudo-element, and catching tap-stealing in the same pass. 554 controls across seven routes at three widths came back clean. The harness was wrong three times before the app was wrong once, which is the part worth remembering: `transition-all` meant the first run measured mid-animation; stripping the media condition off `sm:pointer-coarse:*` rules applied them at every width and collapsed the search field to 16px; and probing the four *corners* fails for anything `rounded-lg`, where a corner has no hit area at all. What it then found that the plan had not: the brand mark is a 32px link, `text-xs` sidebar rows reach 40px where `text-sm` ones reach 44 under the same padding, icon-only buttons using the *text* sizes were 38px wide and so needed `min-w` rather than only `h`, and the switch's pseudo-element came out 42×42 because an absolutely positioned pseudo-element is sized from its origin's *padding* box and the switch has a 1px transparent border. Folded in, because it is the same surface: the mobile drawer stayed open behind Profile and Settings, since `UserMenu` never received the `onNavigate` every other link in the drawer gets — and closing was each link's job, one forgetful component away from recurring. An effect on `usePathname` was rejected by `set-state-in-effect`; deriving it from the path the drawer was opened on passed the lint and reopened the drawer on *forward*, where the paths match again; a `popstate` listener has no equivalent failure. Under it, a delegated handler closes the drawer for any link inside it whatever the link remembers. Two more bugs of that family fell out on the way: the same-page tap, and back/forward never closing it at all.

71. **Mobile scroll model & shell measurement** (`feature/mobile-scroll-model`) — Branch 4, and the one that changed a premise rather than a breakpoint. Below `md` the document scrolls: `body` is `min-h-full md:h-full md:overflow-hidden`, and the top bar is `sticky … md:static` to stay reachable over it. A pinned body cost the phone three things only a moving *document* can give — the URL bar auto-hides only while the document scrolls, pull-to-refresh needs the same, and Next's scroll-to-top on navigation was aiming at a box that never moved. From `md` up the pinned frame is exactly as it was. Viewport heights are `dvh` throughout, `vh` being the *largest* viewport, a size a phone only has mid-scroll. The auth shell needed both halves spelled out (`min-h-dvh md:h-dvh md:overflow-y-auto`) or a tall register form would be clipped from `md` with nothing left to scroll it, and the marketing layout went `h-full` → `h-dvh` because a child's `height: 100%` against a `min-height` parent computes to `auto`, and that shell's nav listens to its own scroller. The 768px cliff — content ~319px *narrower* at 768 than at 767 — was the third goal, and neither option on the table survived: moving the rail to `xl` deletes persistent navigation from 1024–1279, and an icon rail means designing a second navigation, where collections collapse to identical coloured dots. The reframe is that the cliff is not a breakpoint bug but a measurement one. `StatBand` and `CARD_GRID` were asking the *window* how wide they were and subtracting a guessed 319 (sidebar 256 + padding 48 + scrollbar 15), which pessimized desktop — four columns waited for 1184 although they fit at 923 — and made the collapse toggle inert, since collapsing the rail hands the layout 256px no component can see when the viewport has not moved. `main` is now `@container/app` and both query it: 848/1184 became 520/860, and the card grid's `sm`/`lg` became 560/704, the tightest arrangement the viewport rule already produced. Only the rail's *default* moved, not its existence. `collapsed` is three-valued — `null` follows the CSS default, or an explicit open/closed from the toggle — and `null` renders `invisible w-0 xl:visible xl:w-64`, in CSS so there is no first-paint flash, and `invisible` rather than a clipped zero-width box because closed is now the default on every tablet and a clipped box keeps its links in the tab order. Across 1279 → 1280 content goes 1216 → 961, still above the 860 four-column stop, so nothing changes shape at the step. Two defects came out of the browser pass. The create-item dialog scrolled into a screen of blank space, and `dvh` was not the cause: it had two independent scrollers whose caps knew nothing about each other (`100dvh−2rem` on `DialogContent`, `60vh` on the form body), so the dialog reported 885px of scroll for content its own child had already clipped into 621. Sizing the inner scroller from the dialog was tried twice and leaked both times; removing it is the fix, at the cost of a footer that scrolls with the form. And six 44px coarse targets came to 345px of a 345px bar at 360, clipping the primary `+` on a 375px iPhone — so below `sm` the two create buttons are one `+` menu, which meant the top bar taking ownership of both dialogs, a menu item not being able to double as a dialog trigger; `CreateItemDialog` and `CreateCollectionDialog` now accept optional `open`/`onOpenChange` and keep their own trigger when nobody passes them. The trap worth carrying forward: an *arbitrary* container variant is emitted before a *named* one whatever the class order says, so pick one kind and stay in it — all four stops here are arbitrary, verified by byte offset in the built CSS. Deferred: persisting the collapse choice to `localStorage`, which needs a pre-paint inline script.

72. **Mobile code editor** (`feature/mobile-code-editor`) — Branch 5, the last of the responsiveness effort. Monaco does not support touch: it renders its own DOM and drives a hidden textarea, so the platform's caret handle, selection grips and magnifier have nothing to attach to, and placing a cursor mid-word on a phone is a fight. So `CodeEditor` splits by direction rather than by device — reading keeps monaco, where the highlighting is the whole point and there is no caret to place, and *writing* under a coarse pointer falls back to the plain textarea `MarkdownEditor`'s Write tab already was. That textarea moved to `ContentTextarea` so it is one surface rather than two that resemble each other, and the frame, the window dots and the language label are unchanged either way: what differs between reading and writing on a phone is the highlighting and nothing else. Rendering the fallback *instead of* `<Editor>` rather than hiding one of the two is also what keeps monaco off the phone entirely — `@monaco-editor/react` fetches several megabytes from a CDN when the editor mounts, and a fresh load into the create dialog was measured making zero requests matching `monaco` or `jsdelivr`. The condition is `(pointer: coarse)` read through `useSyncExternalStore` over `matchMedia`, not a width breakpoint (branch 3's rule: a touch laptop at 1440px has the problem and a mouse at 390px does not) and not `useState` in an effect (the shape the React Compiler rejected in branch 4); the server snapshot is `false`, so SSR and first paint agree and a phone corrects itself on hydration. Two rules came out of it into `lib/editor-metrics.ts`, both *rendering* rules that are never written back. `renderedFontSize` floors the editor at 16px under a finger, because iOS Safari zooms the page in on any focused control below that and does not zoom back out — the default preference is 13 and the dropdown offers 12, so every editor on a phone was doing it, the markdown one before this branch existed. Storing the floor was rejected (a phone would rewrite the preference a desktop then inherits), as was `maximum-scale=1`, which is the usual fix and an accessibility failure. `editorMaxHeight` caps the 400px ceiling at 60dvh, which changes nothing on a desktop or a phone held upright — 60% of 667 is exactly 400 — and only bites on a landscape phone, where 400px of editor was the whole screen; monaco needs it as a number because it will not scroll itself unless it is told its height, so the same rule exists twice, as `EDITOR_MAX_HEIGHT_CSS` for the panels the stylesheet sizes and as a function for monaco, and the `dvh` share is a whole number because `0.6 * 100` is `60.00000000000001`. Verified by stubbing `matchMedia` before hydration and measuring both directions at three viewports: 234px in landscape, 16px in every editable surface, autocapitalize and autocorrect off for code and left alone for prose. One thing deliberately not verified — whether a touch drag inside the *read-only* editor steals the drawer's scroll, which needs a real device and is noted in project-overview.md §11.

77. **Stripe core infrastructure** (`feature/stripe-core-infrastructure`) — everything the billing integration needs before a single Stripe call is made, and deliberately nothing that makes one: no source file behaves differently at the end of it. The proxy exclusion landed first and is the reason the phase was split this way — `src/proxy.ts` denies by default, so without `api/stripe/webhook` in the negative lookahead Stripe's `POST` would take a 302 to `/sign-in`, be recorded as a failed delivery, retried with backoff for days and eventually disabled, while the route handler is never invoked and nothing is logged on this side either. Shipping it before the route removes the possibility of debugging that. The webhook path only, not `api/stripe` — checkout and the portal are session-authenticated and stay behind the proxy. `src/lib/stripe.ts` follows `r2()` and `resend()` exactly: `server-only` despite living in `lib/`, lazily constructed so `next build` cannot be made to require the secret key, and `billingOrigin()` reading `AUTH_URL` rather than inventing a second name for the deployment's canonical origin. The API version is pinned to `2026-07-29.dahlia`, read off the installed `stripe@22.5.0` rather than copied from the plan document, which by then named the year-old `2025-06-30.basil`; typing the constant as `Stripe.LatestApiVersion` turns a future SDK bump into a build failure instead of a silent behaviour change. `src/config/billing.ts` maps cycles to Price ids through functions rather than module constants, for the same lazy reason, and `ENTITLING_STATUSES` includes `past_due` — a failed payment is Stripe's three-week retry window, not a cancellation, and almost all of them are an expired card, so revoking the same day punishes a paying customer for what their bank did; revocation still happens, when Stripe gives up and moves the subscription to `canceled`, which is not in the set. 78. **Stripe integration and UI** (`feature/stripe-integration-and-ui`) — the half of the billing work that actually talks to Stripe: `server/billing.ts`, the webhook, the checkout and portal actions, the settings billing panel, the account-deletion gate, and the free-tier count checks at the write boundary. The webhook lives at `/api/webhook/stripe` rather than the planned `/api/stripe/webhook`, which meant amending the Phase 1 proxy exclusion; the compiled matcher was checked to confirm that one path and nothing else is open. `syncSubscriptionState` reads the subscription back from the Stripe API instead of applying the event payload, which is what makes replays, duplicates and out-of-order deliveries all converge on the same row — no event log, no processed-id table — and it uses `updateMany` so an event naming a customer this database has never heard of is a no-op rather than a P2025 answered with a 500 and retried forever. 79. **Billing integration test, and the two bugs it found** (`feature/billing-integration-test`) — the manual Stripe checklist was disproportionate: creating an account, cancelling it, and simulating a month passing, by hand, before every billing change. `npm run billing:test` replaces it. A vitest suite with its own config (`vitest.integration.config.ts`, excluded from `npm test` by filename) drives a real test-mode subscription through its whole life — created, cancelled, reinstated, cancelled outright — and asserts what our own functions write after each step. Fourteen assertions, fifteen seconds, no browser and no waiting. It had to be vitest rather than a `scripts/*.ts`: the modules under test are `server-only`, and Node throws on importing that package outside a React Server Component, which the existing test alias already solves. It creates a throwaway user row and its own Stripe customer, deletes both afterwards, and refuses to run unless `STRIPE_SECRET_KEY` is a test key — the demo account and its live subscription are never touched. The suite paid for itself immediately by finding **two real bugs, both live in production**. The first: the customer portal expresses "cancel at period end" as `cancel_at`, a timestamp, and leaves `cancel_at_period_end` **false** — the opposite of what setting the flag through the API does. Every gate read only the flag, so a subscription cancelled the one way a real user can was invisible: the panel promised a renewal, and `willBillAgain` returned true, refusing account deletion to exactly the person who had cancelled as instructed — the regression the whole design existed to prevent, defeated by reading the wrong field. `endsWithoutRenewing` now takes `cancel_at_period_end ? periodEnd : cancel_at` and compares it against the current period's end, because a `cancel_at` several periods out still bills in the meantime. The second surfaced during manual testing right after: the delete dialog branched on `isPro`, but someone who has cancelled is still Pro until their period ends *and* is perfectly deletable — so it told them to cancel, they cancelled, and it told them again, with no way out. `AccountSettingsViewModel.isPro` became `subscriptionBlocksDeletion`, derived as `isPro && !stripeCancelAtPeriodEnd` from a `findUnique` that was already running, and the rename is the point: a boolean called `isPro` invites precisely that mistake. Both fixes were verified by reverting to the broken rule and watching the new tests fail. The lesson the suite itself learned: its first version set `cancel_at_period_end: true` through the API and passed, testing a path no real user takes — it now drives `cancel_at` the way the portal does.

80. **Keep the Stripe customer on account deletion** (`feature/preserve-stripe-customer`) — `endBillingRelationship` was one `customers.del()`, which is the blunt version of the right idea. A deleted Stripe customer retrieves as `{ id, deleted: true }` and nothing else: the name and email are destroyed, so every invoice it paid is left with nobody attached to it. That costs three things a real business needs — reconciling a charge to a person for tax, answering "I was charged and my account is gone", and any view of who churned — and it was noticed the moment a cancelled subscriber was looked for in the dashboard and could not be found. The concern that had motivated deletion was a stored card outliving the account, and the fix for a stored card is to detach the card; the customer record is not what holds payment credentials. It now cancels any subscription still running (immediately, not at period end — the gate has already established nothing more will be charged, but a subscription scheduled to lapse next month should not sit live against an account that is gone), detaches every payment method, and writes an `accountDeletedAt` metadata key. Stripe merges metadata on update, so the `userId` written at customer creation survives, which is what still ties an old invoice back to a row that no longer exists. Each step is independently forgiving: `resource_missing` on the subscription no longer abandons the card detach, which the previous single try/catch would have done. Verified against the real account after a full round trip — customer alive with its name and email, subscription in the cancelled list, zero payment methods attached, both metadata keys present. The distinction that makes this safe is that a *past charge* keeps its card brand and last four digits and always will: that is a financial record backing a receipt or a dispute, not a reusable credential, and detaching removes only the token that could be charged again. Plan §6.5 carries a superseded note rather than an edit, since the redaction paragraph beside it is still the right escalation path for an actual erasure request.

88. **AI explain code** (`feature/ai-explain-code`) — The third Phase 5 feature, and the first AI action that runs over an item being *read* rather than written: an Explain button in the code block's window header asks `gpt-5-nano` what a snippet or command does, and the answer renders as markdown behind Code / Explain tabs in the same frame. Nothing is persisted — regenerated per click, so no column and no migration. It still takes an `ItemDraft` rather than an id, because passing an id would re-read a body the drawer already fetched and would describe the stored row instead of what is on screen. Most of it reuses 84 and 87 (`guardAiRequest` in its documented order, its own `aiExplain` bucket, `canUseAi`), and it departs in four places, each deliberate. **No `json_object`**: those two want a *field* out of the answer, here the whole response is the answer and it is a markdown document, so wrapping it would pay tokens for the model to escape every newline into a string literal and buy a parse that can fail on a perfectly good document — `parseExplanation` still understands a whole-response fence and an object it never asked for. **`reasoning: { effort: "low" }`**, the only call that sets it. **`max_output_tokens` 6000, not the 3000 first shipped**, which truncated roughly every third click; the correction is not that a bigger number is worth paying for but that the small one was never cheaper — a ceiling is not a reservation, so raising it costs nothing on calls that already succeed, while running out mid-thought bills the input and reasoning tokens with no response to show for it. **10 requests an hour, not 20**, this being the most expensive call in the product and the only one whose button sits on a surface you reopen constantly. The type gate is enforced in the action rather than only hidden in the UI, since the type is interpolated into the prompt and a free-text value is an opening to write the model's instructions from the client. The icon collided with the Prompt type for the second time — the spec again asked for `Sparkles`, which 85 had already taken off the Suggest Tags button — and the replacement took two passes: `BookOpen` was rejected on sight for weight, which is the rule now recorded at the call site (light and geometric before clever, since the word "Explain" beside it carries the meaning), landing on `MessageSquareText`. Three unrelated fixes rode the branch as their own commits. **Single-tilde strikethrough** was found by the feature itself: GFM accepts `~struck~`, so an explanation mentioning `HEAD~1` twice had its middle silently deleted and rendered as prose saying the opposite of what was written — now off via a shared `MARKDOWN_PLUGINS` list, since it is a correctness setting a call site must not be able to forget, and tested by rendering rather than by asserting on the option object. **Item cards had no fixed height**: `CARD_GRID` stretches its children, but the grid item is `ItemList`'s overlay wrapper rather than the card, so the wrapper grew and the article inside sat in a taller box — `h-full` fixes the row, and pinning the tag row to one line with a `+N` count fixes the grid, which matters across pages because a grid sized to its tallest card renders the same list at a different height on page 2. That also stopped the click overlay extending past a short card into the gap, which `ItemList` already claimed it did not. **The drawer's action row** hovered at `bg-muted/50`, close enough to the panel that it did not read as buttons until the pointer was already on one.
89. **AI prompt optimizer** (`feature/ai-prompt-optimizer`) — The fourth and last Phase 5 feature: an Optimize button in the markdown editor's header, in the drawer's *read* mode, asks `gpt-5-nano` to rewrite a saved prompt; the answer arrives behind Original / Optimized tabs with a list of what changed, and **Use This** saves it. Structurally it is 88 with the surface moved — same `guardAiRequest` order, its own `aiOptimize` bucket at 10/hour (matching explain, since it too is clicked while reading and returns something as long as its input), and the same opt-in prop shape, so the create and edit forms render the same editor without the button rather than hiding it. Three things are its own. **It is the one AI feature whose input is itself a prompt**, which `docs/ai-integration-plan.md` §12 flagged: a stashed prompt reading "ignore previous instructions" is ordinary content here, not a contrived attack. The instructions name the text as delimited data never to be followed, `buildOptimizeInput` wraps it in markers and strips those markers out of the body first — a boundary the data can close is not a boundary — but neither is claimed to be airtight, and the containment that actually holds is architectural: the rewrite is only ever *shown for review*, never executed, never fed onward, and never written without the accept click. **`unchanged` is a success, not a failure.** The ask was "refine, *if needed*", and a model told to optimize will always find something to change, so the prompt asks for the original back with an empty change list and the button reports "already reads well" instead of opening a review of a rewrite that is not one; it is compared against the *untruncated* draft, or a rewrite that silently drops the tail of a long prompt would report itself as no change. **The save names only `title` and `content`.** The spec had flagged rebuilding the full `UpdateItemInput` as this feature's most dangerous bug — dropping an item's tags or collections on accept — and reading `updateItem` showed the opposite: `tags` and `collections` are relation writes guarded by `tags && {...}`, and the optional columns are `undefined`, which Prisma skips, so an absent field means "leave alone" *by contract*. Omitting is therefore safer than copying, because a field the drawer forgot would clear a column rather than preserve it; `title` is sent only because the schema requires a non-empty one. Smaller notes: `json_object` unlike explain, since this answer has two fields rather than being one markdown document; reasoning left at the default `medium`, because a shallow rewrite is worse than a slow one when the user is being asked to replace their own text with it; `Sparkles` after all, the icon 85 and 88 both had to give up — right here because this is the app's mark for generative *transformation* rather than commentary, which is what tags and prompts already use it for. `isOptimizablePromptType` is a literal `=== "prompt"` rather than a catalog property, since no property means "is a prompt" other than being one, and notes are excluded deliberately: rewriting someone's notes is a different feature. `MarkdownEditor.test.tsx` needed the action stubbed — importing a `"use server"` module pulled Auth.js and `next/server` into a component test that vitest cannot resolve. One unrelated fix rode the branch as its own commit: `/feature complete`'s files-changed table was built from `git diff HEAD~1` with no `..HEAD`, which compares against the **working tree** rather than the last commit, so every uncommitted file in the folder was reported as part of the feature — it now invokes the global `recap` skill, which pins both ends, joins `--name-status` to `--numstat` for real counts, and does not parse `--stat`, whose paths are abbreviated and whose width follows the terminal.

111. **"Delete my account" now deletes the files too** (`feature/r2-account-deletion-cleanup`) — §11's retention hole: `deleteAccount` deleted the `User` row, Postgres cascaded every item away, and `deleteObject` was called from exactly one place that was not this one, so every file the account had uploaded stayed in the bucket forever with nothing pointing at it. §11 framed the fix as a choice between reading `Item.fileKey` before the delete and a scheduled prefix sweep; what shipped is the second mechanism on the first schedule, which is strictly better than the first. `deleteUserObjects(userId)` in `lib/r2.ts` lists and deletes the `users/<id>/` prefix a page at a time, so the keys never have to survive the cascade — `buildObjectKey` is the only thing that mints a key and `isOwnedKey` already treats that prefix as proof of ownership, which makes the prefix the authority on what belongs to the account, and no query is needed at all. 114. **The idle session window drops from thirty days to seven** (`fix/shorter-session-lifetime`) — the interim half of §11's session-revocation question, taken because it is one line and the full answer is not. Nothing can invalidate a JWT already issued: the token carries no version claim, so changing a password from `/settings` or a reset link leaves every other device signed in and a compromised password cannot be locked out. The real fix is `sessionVersion` on `User` compared per request, which is a database read per request — most of the reason `strategy: "jwt"` was chosen over `"database"` in the first place, since the edge proxy authorizes without touching Postgres. So it reopens the session strategy rather than patching it, and stays deferred. What `maxAge: 7 days` actually buys is worth stating precisely, because the note it replaces overstated it: Auth.js re-issues the token on activity, so this is the **idle** window. It closes the abandoned-browser and stolen-laptop cases four times sooner than thirty days did, and does nothing whatsoever about a session an attacker is actively using — that one refreshes itself. Seven rather than fourteen because the cost is asymmetric: a re-login is an inconvenience, an un-evictable session on a device you no longer control is not.

115. **"Recent" collections start meaning recent** (`feature/collection-activity-recency`) — §11's oldest quiet lie. §8 promised recency was `updatedAt`, and the dashboard's recent cards and the sidebar's recent list both genuinely ordered by it — but nothing moved the column.
