24. **Email verification on registration** (`feature/email-verification`) — New credentials accounts are created unverified and cannot sign in until they click a single-use link, making `User.emailVerified` a signal the account-linking work can trust. Tokens are 32 random bytes stored as a SHA-256 digest, so a database read yields no working links; the unverified check sits *after* the bcrypt compare, where naming the account's state discloses nothing the caller has not already proven, and the decoy-hash timing guard survives intact. GitHub sign-ups are marked verified by a `linkAccount` event, since the provider's profile mapping leaves the column null and the ambiguity would make it useless. The whole feature was written, discarded, and rewritten: delivery fails at Resend, not in this code — every send from the account fails asynchronously with "Domain is not verified", including `onboarding@resend.dev` to Resend's own `delivered@resend.dev` simulator, with `POST /emails` returning 200 and a null error throughout. The first attempt hid that behind a console-printed link and so reached "done" without ever sending an email; this one keeps the workarounds in `scripts/` (`email:test` polls `last_event` until it settles, `user:verify` marks an account by hand) where they cannot make the product lie. Resend support confirmed the outage as their own defect and fixed it; `onboarding@resend.dev` now delivers, though only to the account owner's own address, so a verified domain is still required before real users can receive anything.
25. **Review follow-ups** (`fix/resend-timing-oracle`) — A review pass over the two unpushed auth features turned up one real defect. `POST /api/auth/verify-email` equalized its response *body* across every outcome but not its *timing*: only the unverified-credentials path issued a token and awaited a round trip to Resend, so latency alone separated those accounts from unknown, already-verified and OAuth-only addresses — the enumeration oracle `ABSENT_USER_HASH` exists to close, reopened one file over, in an endpoint whose own docstring claimed parity with it. The lookup, token issue and send now run in `after()`, behind a response that has already left. Also corrected the header of `scripts/verify-user.ts`, which still described the Resend outage as ongoing after `5e6b91a` fixed that wording everywhere else.
26. **Password reset** (`feature/password-reset`) — A "Forgot password?" link on the sign-in form and the flow behind it: `/forgot-password` asks for an address, a single-use link lands on `/reset-password`, and the new password is written by `POST /api/auth/reset-password`. Reset tokens live in the same `VerificationToken` table as the confirmation ones, which is the whole risk of the feature: that table has no purpose column and a token is found by its digest alone, so without a namespace a *verification* token posted to the reset route would let anyone who can receive that email set a password on the account. Both purposes now carry an explicit `identifier` prefix — including verification, which previously used the bare address, because a purpose defined as "no prefix" has to exclude every future purpose by name and the failure mode of forgetting is silent. The request endpoint answers 200 for everything with the lookup and send in `after()`, the same enumeration parity `POST /api/auth/verify-email` settled on; the reset endpoint is free to name its failures, since the caller is identified by a token they had to receive rather than an address anyone can type. Three smaller decisions: a reset link also sets `emailVerified` (receiving it is the same proof the confirmation email asks for) but never overwrites an existing timestamp; the token is checked before the bcrypt hash and consumed after, so junk input cannot buy 500ms of CPU on an unrated endpoint and a hashing failure cannot spend a live link; and `/reset-password` is reachable *with* a session, unlike the other signed-out routes, because a reset link is opened from whatever browser the mail client hands it to. An account with no password gets a "you sign in with GitHub" email instead of silence, which discloses nothing — it only ever reaches the address that was entered. Rate limiting is still missing, and JWT sessions still have no version claim, so a reset cannot evict a session held by whoever knew the old password.
27. **Honour the sign-in callback URL** (`fix/sign-in-callback-url`) — The proxy had been writing `?callbackUrl=` on every bounce and nothing ever read it: both sign-in paths hardcoded `redirectTo`, so a signed-out deep link to a collection always dumped you on the dashboard, and the most common bounce of all decorated the address bar with `?callbackUrl=%2F` for no benefit. Sign-in now returns you where you were headed. A Server Action cannot see the URL of the page that invoked it, so the value travels as a hidden field in both forms rather than being read from the request — which makes it exactly as forgeable as the query param, hence `resolveCallbackUrl` validating at both ends. It accepts same-origin relative paths only: absolute URLs, protocol-relative `//host`, and the `/\host` form browsers normalize into it are all refused, since honouring any of them is an open redirect that inherits the credibility of the site the user just trusted with a password. The auth pages are refused too, as returning to `/sign-in` after signing in is a loop. `welcome=back` stays on the default destination alone: `WelcomeToast` is rendered only by the dashboard home and clears its flag with a hardcoded `router.replace("/")`, so attaching it to a deep link would raise no toast, strand the param, and one day redirect people off the page they asked for. The proxy's route sets moved to `lib/auth-redirects.ts` because the guard needs the same list and two copies would drift.

32. **Recover from a session whose user no longer exists** (`fix/stale-session-user`) — A JWT outlives the row it names, and `getCurrentUser` threw when that row was gone: every page answered 500 with no way out of it, because the token still parses, so the proxy treats the visitor as signed in and redirects them off `/sign-in` back to `/`, which throws again. The render now redirects to `GET /api/auth/stale-session`, which clears the cookie and returns them to the sign-in form. It has to be a route handler rather than a `signOut()` where the problem is detected — server components may not write cookies, and the cookie is the one thing that ends the loop. The handler re-checks that the row really is missing before clearing anything, which is what makes it safe to expose: a `GET` that unconditionally signed people out would be logout CSRF, droppable by an `<img>` tag on any page. `SessionUserMissing` joins the codes in `lib/auth-errors.ts` so the form explains itself instead of inviting a retry that cannot work. `getProfile` keeps its throw — it fires only when the row disappears between two queries of one request, which is a genuine race and not a stale cookie. This is not session revocation: a live JWT for a *surviving* account is still untouchable, which remains the `sessionVersion` question deferred in §11. It only makes an already-fails-closed case fail closed gracefully.

33. **Rate limiting for auth** (`feature/rate-limiting-auth`) — Upstash Redis sliding windows on the five auth entry points, closing the gap Phase 1 deferred. The credentials limit lives in `authorize` rather than in the sign-in Server Action, because `POST /api/auth/callback/credentials` is public and a script driving it never touches the form — limiting the action would have protected the only caller that was never the threat; it throws a `CredentialsSignin` subclass like the unverified-email one, so the message reaches the form through the existing `code` path, at the cost of not being able to carry the remaining minutes. Sign-in and resend key on IP *and* email: per-IP alone locks out everyone behind one office NAT, per-email alone hands an attacker a way to lock a known address out of its own account. The other three key on IP alone, since mixing in the submitted address would hand a fresh budget to every address a script invents, which is the abuse itself. The two enumeration-safe routes now have one answer that differs, and it is safe — a 429 depends on the caller's own request count, never on whether an address exists — but both forms had to stop claiming a link was on its way for a request the server refused. Writing the fail-open test against a real transport showed fail-open was not working: the SDK retries five times with exponential backoff (~4.7s, so every sign-in stalled that long during an outage) and had no timeout at all, and a `catch` cannot fail open on a promise that never settles, so a hung Upstash would have hung sign-in indefinitely. Retries are pinned to one and checks bounded at a second. Two things left as they are, with the reasoning recorded in `rate-limit.ts`: the retry estimate is optimistic, because the SDK's `reset` is the next window boundary rather than when this caller regains capacity, and reporting the truth means reimplementing decay the library does not expose; and the module carries `import "server-only"` despite the spec naming a `lib/` path, since that directory is client-reachable and the REST token must not reach a browser bundle. Found but deliberately not fixed here: `ResendVerification` renders a `<form>` inside `SignInForm`'s `<form>`, which is invalid HTML, so its submit handler never runs and the resend control has never worked — pre-existing on `main` and tracked separately, which leaves the 429 path in that one component verified by inspection only.

34. **Resend control could never be clicked** (`fix/resend-nested-form`) — `ResendVerification` rendered a `<form>`, and its only caller renders it inside `SignInForm`'s `<form>`. A form cannot contain a form: the parser drops the inner tag, so `onSubmit` never ran and "Resend link" did a native GET to `/sign-in?email=…`, with React reporting "In HTML, `<form>` cannot be a descendant of `<form>`" in the console. The one escape hatch for an account with an unconfirmed address had therefore never worked — found while trying to verify the rate-limit 429 in that component, not by anything the rate-limiting change did. Now a plain container with a `type="button"`, which avoids the nesting rather than trusting the parent to keep its distance. Two consequences of the field now belonging to the sign-in form: it carries no `name`, or a second `email` entry would ride along with the credentials, and Enter is handled explicitly, or the key would resubmit the password that just failed. Verified in a browser end to end — no navigation, no hydration error, the 429 rendering below the row as intended, and Enter issuing the request rather than the sign-in.

38. **Item detail drawer** (`feature/item-drawer`) — Clicking an item card opens a right-side Sheet with the item's full detail; there is no separate item page. The drawer opens on the summary the card already carried and fetches only what a list query never selects — the body, the collections holding it, the creation date — so the title, type, tags, and description are on screen before the request is sent, and the skeleton covers three fields rather than the whole panel. `getItemDetail` puts ownership in the `where` rather than checking the result, which makes another user's id indistinguishable from a missing one; a test pins that by filtering the Prisma stand-in only on the keys actually present, so a refactor to `findUnique({ where: { id } })` fails that test instead of quietly serving someone else's item — verified by making the change and watching only that test break. `GET /api/items/[id]` is a route handler because the drawer distinguishes 404 from a retryable error, the same rule that made `api/auth/register` one. Two structural decisions came from constraints rather than taste: the trigger is an overlay button rather than the card itself, because a `<button>` may contain only phrasing content and `ItemCard` renders an `<article>` with a heading — the same invalid-markup class as the nested `<form>` that once left the resend control unclickable — which also leaves `ItemCard` untouched and still usable as plain markup; and the React Compiler's rule against synchronous `setState` in an effect ruled out clearing the fetch state there, so `ItemList` keys the drawer by item id instead and holds `open` separately from `selected`, which incidentally bought the close animation. The collection page was wired alongside the dashboard and item-type pages the spec named, since all three render the same card and one that looks identical but does not open reads as a bug rather than a smaller scope. Deliberately not built: every action-bar button except Copy is inert, because they are mutations and mutations are the next feature — they render in their resting state, so a favourited item still shows a filled star; syntax highlighting and line numbers, which the reference screenshot has and Phase 3 owns; and file/image rendering, since nothing can create a FILE item before Phase 4 and the seed has none. Committed alongside a second, unrelated change made on the same branch at request: the DevStash logo and wordmark are now one link to the dashboard, opt-in per call site because the signed-out auth shell renders the same component and the proxy would bounce it from `/` straight back to `/sign-in`.

39. **Item drawer edit mode** (`feature/item-drawer-edit`) — The pencil button that shipped inert now switches the open drawer into an inline edit form; collections and dates stay on screen read-only, and the item's type is not editable at all, since accepting it would let a payload re-type an item while `contentType` and the populated content column stayed as they were. The load ran `/project-sync` over the spec first, which caught three course-isms before they became code (`lib/db/items.ts`, `ItemDetail`, `auth()`), and the write was placed directly in the action rather than behind a query function, so `server/` stays read-only as §9 describes. The design decision that mattered is *absent versus empty*: the form renders only the fields a type owns and submits only those, so a snippet's payload has no `url` key, which the schema preserves as `undefined` for Prisma to skip — while an emptied input sends `""` and clears the column. Without that split, one type's form would silently wipe another type's column, and it is the first thing the tests pin. Tag writes are `createMany({ skipDuplicates })` then `set` rather than `set` alongside `connectOrCreate`, because the ordering of those two in one nested write is not something the docs guarantee; ownership sits in the `where` as `getItemDetail` already does it. One bug surfaced during the build rather than from the spec: the drawer rendered from the card's summary, but `ItemList` holds the clicked item in `useState`, so `router.refresh()` updates the cards behind the drawer and never that prop — saving a new title would have left the old one in the header. It now reads from the fetched detail once that lands, which incidentally makes the Updated date tick over on save. Unit tests cover the schema's normalization and validation only; the Prisma write path is type-checked but never executed, which was flagged rather than papered over.

40. **Delete items from the drawer** (`feature/item-delete`) — The trash button that shipped inert now opens an `AlertDialog` naming the item, and `deleteItem` removes the row. Ownership sits in the Prisma `where` for the third time in this file, so another user's item is refused by the same path as a missing one, and the test asserts the row is *still there* afterwards rather than only that the call failed — a delete that returns an error while destroying the record would pass the weaker assertion. One `delete` covers everything: `ItemCollection` declares `onDelete: Cascade` on its item side and the implicit `ItemTags` join does the same, so the join rows go without a transaction, while global `Tag` rows survive because they are shared across users. The confirm is a plain button rather than `AlertDialogAction`, which dismisses on click — the action can fail, and a dialog that has already closed has nowhere to report it — the same reasoning `DeleteAccountDialog` records, though the typed-email confirmation is not repeated here: an item is one row a user can re-create, not their whole account. It is a hard delete, which the dialog says out loud, since `deletedAt` and a trash view are still an open question in §11 and adding either is a schema change rather than a change to this. The success toast is green by the `richColors` outcome convention — questioned during review on the grounds that green reads as celebratory for a destructive action, and kept, because the alternative that actually works is a neutral toast paired with Undo, which a hard delete cannot offer. Verified by hand rather than in a driven browser; `npm run db:seed` restores the demo content, being authoritative rather than additive.

41. **Create items from the top bar** (`feature/item-create`) — The disabled New Item button now opens a shadcn Dialog: pick one of five types, fill in the fields that type owns, and `createItem` writes the row. Create stays a modal while view and edit stay a Sheet — a divergence from §8, confirmed at load rather than drifted into, since creating is the one item flow with no card underneath for a panel to sit beside. Three things the payload is not trusted with: `userId` comes from the session, the item type is resolved from the submitted *name* with `findFirst({ name, userId: null })`, and `contentType` is read from the catalog — and the schema strips the content columns the chosen type does not own, so no hand-made payload can put text in a link. The type test seeds a *custom* `snippet` ahead of the system one, so a lookup that stopped filtering on `userId` returns the wrong id and fails. `file` and `image` are excluded by content type, not by Pro gating: `ENFORCE_PRO_LIMITS` is still false, so an entitlement check would have offered them to everyone, and their content is an R2 object nothing can upload before Phase 4 — the creatable list is asserted against the catalog, so adding one there fails the test until the upload exists. `itemTypeOwns()` replaced the edit form's private copy of the same rule and `Field` moved to `components/ui`, leaving one source for both forms. The placeholders were reworked twice on feedback and settled by checking the research rather than taste: never restate the label (an "Enter title" under a "Title" label is the documented anti-pattern, and makes an empty field look filled), instructions where the field is open-ended, examples where format carries the information.

42. **Monaco code editor** (`feature/code-editor`) — Snippets and commands now render in a Monaco editor styled as a small macOS window — traffic-light dots and the resolved language in the header — in all three places an item body appears: read-only in the drawer, editable in the create dialog and the edit form. Notes, prompts, and links keep the textarea, and the split is made on `itemTypeOwns(name).language`, which already meant exactly "this type's content is code", so no second list of types can drift from the first. Monaco loads from a CDN rather than the bundle, keeping several megabytes out of the build at the cost of needing a network on first mount; its version is pinned to the exact `monaco-editor` the option types come from, because the wrapper's default build is a *different* version and the two disagree on option shapes — `hover.enabled` is a boolean in one and a string union in the other, which is what broke the first build. Free-text `Item.language` is normalized to a Monaco language id in `lib/code-language.ts`, kept out of the component so it could be tested as the pure lookup it is. Two changes came from review rather than the spec: the language input moved above the content in both forms, since it is what the editor highlights by and asking after the code is written is asking too late; and the spec's in-editor copy button was built and then dropped, because in the drawer it duplicated the action bar's Copy exactly and in the forms it was the only one but also the place copying is beside the point. The create dialog also now opens on the type matching the page, resolved against the creatable types so `/items/files` cannot preselect something nothing can create yet. Height follows `getContentHeight()` between 76px and 400px, then the editor scrolls itself with sliders themed to match; word wrap is on rather than a horizontal scrollbar, because the drawer is ~576px wide.

43. **Markdown editor** (`feature/markdown-editor`) — Notes and prompts now render in a Write/Preview editor built on `react-markdown` + `remark-gfm`, in the same three places a body appears: read-only in the drawer, editable in the create dialog and the edit form. Snippets and commands keep Monaco, and the split reuses `itemTypeOwns(name).language` rather than naming the prose types, so the two editors cannot drift apart. Raw HTML stays escaped — `rehype-raw` was never added, since a stored note is untrusted input even when its author is its only reader. The Write panel is force-mounted and hidden by `data-[state=inactive]`, so the caret and scroll survive a look at Preview and `Field`'s `htmlFor` keeps resolving; Preview unmounts, which is what keeps the markdown from being reparsed on every keystroke. Two dependencies were tried and reverted, both after being seen rather than argued about. `@tailwindcss/typography` is calibrated for an article at its own 65ch measure and sizes everything in `em` multiples of it, so even `prose-sm` gave an h1 of 2.14em — and because heading margins are heading-relative, big headings tore big holes above themselves; in a 480px drawer it read as a blog post in a box. The hand-written `.markdown-preview` that replaced it settled at a 20/16/14/13 ramp on 14px body with **`rem`** margins, no heading rules (a README convention that means nothing at this size), tightened tracking, and body text a shade under `--foreground` so headings have brightness left to be distinguished by. `rehype-highlight` went the same way: 352K of highlight.js in the chunk every drawer loads, to colour the occasional command. The fence's `language-*` class is kept and tested as the hook a future highlighter attaches to — `monaco.editor.colorize()` being the option that costs no dependency, at the price of pulling Monaco's CDN payload onto a path that mounts no editor. The preview's scrollbar is repainted from Monaco's three slider colours at its 10px width, a duplicated literal with a pointer at each end, because a JS theme object and a native scrollbar have no shared place to read from; matching it exactly would mean reimplementing an overlay scrollbar, which was declined. Eleven tests render the component to static markup and assert the GFM constructs individually, so dropping a plugin fails loudly rather than silently. The session's real cost was not the code: a corrupted Turbopack cache in `.next/dev` served a stale stylesheet across two full restarts and then 500s, making every CSS change invisible for several rounds — caused by running production builds against a live dev server and killing it mid-write.

44. **File & image upload with Cloudflare R2** (`feature/file-image-upload`) — `file` and `image` join the creatable types: `FileUpload` drops or picks a file, `POST /api/upload` validates it and puts it in R2, and the create dialog submits the returned key with the rest of the form. The instructor's completed repo was inspected first and deliberately not followed. It stores the full public URL in the item row and renders images straight from a public bucket, so its download proxy — which re-fetches that same public URL server-side — authorizes nothing that the URL in the page does not already give away. Here the bucket is private and `GET /api/files/[id]` is the only way in: it looks the *item* up for the signed-in user and reads the key off that row, so a caller can only ever name an item and there is no path string for a `..` segment to defeat. `Item.fileUrl` was renamed to `fileKey` by a hand-written `ALTER TABLE … RENAME COLUMN`, because Prisma generated a drop-and-add that is only equivalent while every value is NULL, and the column now holds `users/<id>/<uuid>` rather than a URL — which keeps a later move to presigned URLs a route change instead of a data migration, and keeps deletion from having to parse a key back out of a URL as the course's does. The key round-trips through the browser, so `createItem` re-derives ownership with `isOwnedKey` rather than trusting it; the original filename and size live in the columns that already existed, and no MIME column exists at all, since `ContentType` set on the `PutObject` comes back on read. Validation is extension-first with the media type checked only when the browser supplied one, because `File.type` is empty for `.md` and `.toml` on most platforms and refusing that would refuse ordinary uploads. Deletion removes the object *after* the row commits and swallows the failure: an orphan nobody can see is a cheaper mistake than an item pointing at nothing. Previews went past the spec on purpose — nine of the ten allowed formats are text, and the renderers already existed, so markdown opens as a note does, the rest highlight in Monaco, PDFs go to the browser's viewer with `#toolbar=0`, and Copy now works on a stashed `.env.example`; SVG is never served inline and previews as its own source instead, and the route gained `X-Content-Type-Options: nosniff`, which only matters once responses are rendered rather than downloaded. Replacing a file is deliberately absent: it is the one mutation with an ordering hazard, and the edit form shows the object read-only instead. The session's real lesson was a CSS one: the drawer had been **384px wide** on every viewport at or above `sm`, because `SheetContent`'s own `data-[side=right]:sm:max-w-sm` out-specifies any `sm:max-w-*` passed in and `cn` cannot merge the two — which is why five labelled toolbar buttons overflowed and put a horizontal scrollbar under file items but not commands ("Download" is wider than "Copy"). Three confident wrong diagnoses preceded finding it. The width is now set on the same variant so the defaults are dropped rather than fought, sized from the floor the toolbar needs, and the labels collapse to icons below `sm`. R2 itself was verified end to end with a throwaway put/get/delete against the real bucket; the HTTP path was checked by hand in the browser.

45. **File list view** (`feature/file-list-view`) — `/items/files` renders as a single-column list of file rows instead of the card grid every other type uses: category icon, filename, size, upload date, and a download button, with the metadata stacking under the name below `sm`. `/items/[slug]` is one route serving all seven types, so the choice is made per type there and `ItemList` gained a `variant` that picks the entry component while the container classes still arrive as `className` — layout stayed the page's business. The rows needed data the list side never carried: `fileName`, `fileSize`, and `createdAt` moved onto `ItemSummaryViewModel`, which `ItemDetailViewModel` now inherits rather than redeclaring. Three narrow scalars on a row already being read, so the rule that list queries never touch `content` / `url` / `fileKey` is intact — and the key is still never selected anywhere, since a file is addressed as `/api/files/[id]`. Doing that exposed a duplicate: `getCollectionPageData` had hand-copied the summary column list, which would have silently fallen a column behind, so `ITEM_SUMMARY_SELECT` is exported and used by both. The icon maps extension → one of five categories rather than reusing `filePreviewFor`, whose answer depends on file *size* — a 2 MB YAML previews as `none`, and an icon must not change because a file grew; a test walks every extension the upload rules allow, so adding one there without adding it here fails. The spec asked for `stopPropagation` on the download button, which turned out not to apply: `ItemList` opens the drawer with a full-row overlay button that is a *sibling* of the row, not a parent, so there is no event to stop and the anchor takes `relative z-10` to sit above the overlay instead. The filename is the row's heading, which would otherwise hide the item's own title, so the title appears in the metadata line when the two differ. `/items/images` was left on the grid — the spec named files only.

46. **Image gallery view** (`feature/image-gallery-view`) — `/items/images` now renders thumbnails instead of item cards: a 16:9 tile per image with the title and date captioned under it, three across on the existing grid. `ItemList` gained an `image` variant beside `card` and `file`, and the wrapper each entry sits in took a `group` class — the drawer trigger is a full-size button laid over the entry as its *sibling*, so a card can never match `:hover` itself and the 5%/300ms zoom had to be `group-hover`. `isRenderableImage` moved out of `file-preview` as its own export and is now the single source for the image branch of both `filePreviewFor` and `isInlineDisposition`: SVG is an uploadable image format this origin deliberately never serves inline, so those tiles show a file-type icon rather than an `<img>`, and keying it on the name alone means a thumbnail cannot disappear because a picture grew past the text preview cap. Two things changed after seeing them rendered rather than in the spec. The spec asked for `object-cover`; the first portrait photograph through it — Michelangelo's David — came out as a torso with the head cropped off, so the picture is `object-contain` inside the same fixed tile: uniform tiles, letterbox bars, nothing cut. And `FileRow` was inverted on the same principle — the item title is now the heading with the object filename on a second line beneath it, where a real upload (`12+Rules+to+Learn+to+Code+[2nd+Edition]+2022.pdf`) had been the row's largest text while the name a person chose sat in grey at the far right. Putting the filename on its own line rather than beside the title is what stopped it being trimmed, which also retired the `sm:` stacking the row needed when four strings competed for one line.

47. **Quick copy on item cards** (`feature/card-quick-copy`) — A copy icon on each item card puts the item's body on the clipboard without opening the drawer, with the drawer's own toasts. The card has no body to copy — list queries never select `content` / `url`, which is what `ItemSummaryViewModel` exists to enforce — so the icon fetches from the same routes the drawer reads, on click, and nothing is loaded for a card nobody copies. That fetch is the whole reason this was not a two-line change: Safari allows a clipboard write only while the triggering gesture is live, and an awaited `fetch` ends it, so `writeClipboardText` hands the *pending* promise to `ClipboardItem` instead and falls back to `writeText` where that is missing. The write and both toasts moved to `lib/clipboard.ts` and the drawer now calls it too, so one action reached two ways cannot start reporting itself two ways. The button lives in `ItemList` rather than in `ItemCard`, because the drawer trigger is an `inset-0` sibling laid over each entry and anything beneath it in the stack is unclickable; being a later sibling is also all the layering it needs, since positioned elements paint in document order. It takes the corner the timestamp occupies and the date fades out as it fades in — `group-focus-within` gives the keyboard the same swap, so tabbing to a card reveals its action rather than leaving an invisible focus target. Which items get one is `copyableSourceFor`, the drawer's rule rather than a new one: a text file copies its contents from `/api/files/[id]`, an image or PDF gets no icon at all, and everything else copies `url || content` from `/api/items/[id]`. It is tested as a pure function because the branch that matters — a picture offering a copy that could never work — is invisible until someone stashes a PNG. An item with an empty body has to be reported by rejecting rather than by disabling the control up front, the way the drawer disables its Copy: the drawer knows the body is empty because it already holds it, and a card cannot know until it asks. File rows and gallery tiles were left alone; the request was the item card.

48. **Link scheme validation and upload rate limiting** (`feature/link-scheme-and-upload-limits`) — Two hardening fixes from a codebase audit, both closing a gap where an existing control stopped one step short. `optionalUrl` used `z.url()`, which validates *shape* and not scheme — probed against the installed Zod 4.4.3, it accepted `javascript:`, `data:`, `vbscript:` and `file:` as readily as `https:` — while `ItemDrawer` renders the stored value as an `href`, so a saved `javascript:` URL ran on this origin when the link was clicked, through both the create and the edit path since both share the field. Bounded with `protocol: /^https?$/` and pinned by tests over all four schemes plus the two that must still work in any case. Only the owner can open their own item's drawer, so this was self-inflicted today; it was fixed anyway because it costs one regular expression and stops being self-inflicted the moment an item is shared or exported. `POST /api/upload` gained the limiter the four auth routes have had since `feature/rate-limiting-auth`: 30 in 10 minutes, checked before the body is read so a refused caller cannot stream 10 MB in first. It is keyed on the **account**, not the IP — the route is behind the session, so the better identifier is available, and an IP would bill one office NAT for everyone behind it — which meant `checkRateLimit`'s second parameter stopped being an IP and was renamed `caller`, with `keyBy` gaining a `"user"` case. This route rather than every mutation because it is the only one that writes to paid storage, accepts 10 MB a request, and stores the object *before* the item row exists, so a loop that never finishes creating an item leaves orphans nothing points at. Three other candidates were checked against the code and rejected rather than built: bcrypt rounds are already 12 and are not a free number to change, since `ABSENT_USER_HASH` is a decoy precomputed at that cost to equalize sign-in timing; there is nothing to debounce yet, because every `onChange` in the item forms and both editors sets local state and `MarkdownEditor`'s Preview unmounts while Write is active, which makes it a Phase 3 concern arriving with search; and `next/image` would *break* two of its three candidate call sites, since `FilePreview` and `ImageCard` read `/api/files/[id]`, an authorized route whose optimizer fetch would arrive without the session cookie. That last one is the downstream consequence of the private-bucket decision — the course's public bucket is exactly why the same swap works there — and the reasoning already lives in `r2.ts` and beside both `<img>` tags. The dev database was checked for rows the new rule would retroactively invalidate: 7 URLs, none of them non-`http(s)`, so no migration.

49. **Break up the item form and upload components** (`refactor/item-form-and-upload-seams`) — Two pure refactors from a survey of oversized components, no behaviour change. The create dialog and the edit drawer were rendering the content, language, and tags fields line for line the same — same labels, placeholders, hint, and the same `showsLanguage ? CodeEditor : MarkdownEditor` branch including its comment, differing only in the `id` prefix — so those three moved to `ItemFormFields` and the editor an item is displayed in can no longer drift from the one it is edited in. Each owns its `Field` as well as its input, because that is the pair which has to agree: `Field` renders the error as `<p id="{id}-error">` and the input must point at exactly that id, so the `aria-describedby` is derived rather than passed. Title, description, and URL stayed inline — they differ in placeholder, `rows`, and `autoFocus` — and there is no wrapper over the whole set, because the two forms order the fields differently and a shared one would have to take the order as a prop. `useItemFormState` was in the plan and dropped after a close read: six `useState` lines are clearer than a hook returning twelve setters, and the duplication that could actually cause a bug was the JSX. `FileUpload` gave up its `XMLHttpRequest` to `useFileUpload` — the first file in `src/hooks/`, which §9 had carried as `(planned)` since the structure was written — along with the response parsing, since an XHR hands back a string rather than something with `.json()`; the uploaded state became a local `UploadedFileRow`, and the component went 223 → 148 lines. The hook returns `progress` and deliberately no `isUploading` beside it: returning the boolean broke TypeScript's narrowing, because the caller renders the percentage inside its own `progress !== null` branch and `number | null` narrows only when the test is the caller's own, which left `aria-valuenow` taking a possible null. `tsc --noUnusedLocals` caught that; `eslint` did not, which is the argument for running both on a refactor. Total code lines rose by about 17 across the item forms, which is what extracting small typed components costs in TypeScript — the payoff is single source of truth, not brevity, and the two form functions still shrank to 225 and 157 lines. Not done, and deliberately: `ItemDrawer`, which is the largest of them at 403 lines but whose toolbar Phase 2 will open anyway when favouriting and pinning become live mutations; `actions/items.ts`, whose two hundred-line functions read top to bottom with every step load-bearing; `SidebarNav`, already factored into four helpers; and the auth forms, where the "fix" is a design change to label styling rather than a defect.
