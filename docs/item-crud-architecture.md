# Item CRUD Architecture


> **As shipped (2026-09-01): this is the plan, not the result.** Item CRUD is live and the design
> largely held, with two path differences worth knowing before following a link below: the
> body-column routing landed as `itemTypeOwns()` in `src/lib/item-schemas.ts` rather than as a
> separate `src/lib/item-content.ts`, and the form pattern it points at is now
> `src/components/settings/ChangePasswordDialog.tsx`, not `src/components/profile/ChangePasswordForm.tsx`.
> The text below is left as written, as a record of what was planned.

A design for creating, reading, updating, and deleting items across all seven system types —
following this project's structure, not the course's.

Generated by `/research context/research/item-crud-research.md`. **This is a design document, not a
description of shipped code.** Item CRUD is roadmap Phase 2 and does not exist yet. Every file under
"proposed" below is new. Sections marked **Exists** describe code you can read today and are the
patterns the proposal is derived from; sections marked **Proposed** are design decisions open to
being overruled.

---

## 1. What exists, and what has to be built

**Exists.** All reads. `src/server/items.ts` serves the dashboard lists and `/items/[slug]`;
`src/server/collections.ts` serves the collection pages. Everything returns view models, and no
component has ever seen a Prisma record. `ItemCard` and `TypeIcon` render any type.

**Exists.** The write pattern, twice over — `src/actions/account.ts` (two Server Actions) and
`src/app/api/auth/register/route.ts` (the one mutation that needed a status code).

**Does not exist.** Any item mutation, any item detail read, any drawer, any form, any Zod contract
for an item, and any `revalidatePath` call anywhere in the codebase.

The gap is narrower than it looks: the read layer, the view models, the type catalog, and the
entitlement helper are all in place. What is missing is a write boundary and the UI that calls it.

```
│   ├── item-content.ts             # ★ new — pure body-column routing, unit-tested
│   └── limits.ts                   #   extend — add canCreateItem()
├── server/
│   ├── items.ts                    #   extend — add getItemDetail()
│   └── item-types.ts               #   extend — add getSystemItemTypeByName()
├── types/
│   ├── item.ts                     # ★ new — ItemActionState + EMPTY_ITEM_STATE
│   └── view-models.ts              #   extend — add ItemDetailViewModel
├── app/(dashboard)/items/[slug]/
│   └── page.tsx                    #   extend — mount the drawer
└── components/items/
    ├── ItemDrawer.tsx              # ★ new — slide-out shell (view / edit / create)
    ├── ItemForm.tsx                # ★ new — shared form, swaps body editor by contentType
    ├── ItemBodyEditor.tsx          # ★ new — the TEXT / URL / FILE branch
    ├── ItemCard.tsx                #   extend — becomes a drawer trigger
    └── TypeIcon.tsx                #   unchanged
```

The split follows `coding-standards.md` exactly: `actions/` owns writes, `server/` owns reads and
view-model preparation, `lib/` holds client-reachable pure helpers and Zod contracts, `types/` holds
compile-time contracts, `config/` holds runtime values.

### Why the pure helpers cannot live in `actions/items.ts`

A `"use server"` module **may only export async functions.** This is not a style preference — it is
enforced by the compiler, and it is already the documented reason `EMPTY_ACCOUNT_STATE` sits in
`src/types/account.ts` rather than beside the action that consumes it
([types/account.ts:4](../src/types/account.ts#L4)).

So the body-routing function and the action state constant *must* live outside the action module.
That constraint is what produces `src/lib/item-content.ts` and `src/types/item.ts`, and it has a
pleasant side effect: a pure function in `lib/` is unit-testable with plain fixtures, which is how
`view-models.ts` and `limits.ts` are already tested.

## 3. Routing: `/items/[slug]`

**Exists**, unchanged by this design. The mechanism is worth restating because it is the one place
the plural/singular distinction bites.

The URL segment is the **plural route slug** (`snippets`, `prompts`, `links`), which is application
config. The database stores the **singular natural key** (`snippet`, `prompt`, `link`). They are
bridged by a lookup map built once at module load:

```ts
// config/item-type-catalog.ts:98
const itemTypeNameBySlug = new Map(
    SYSTEM_ITEM_TYPE_NAMES.map((name) => [ITEM_TYPE_CATALOG[name].slug, name]),
);
```

`getItemTypePageData(slug)` resolves it, returns `undefined` for an unknown slug *or* a type the user
cannot access, and the page calls `notFound()`
([items.ts:82](../src/server/items.ts#L82)). One `undefined` for both cases is deliberate: a
Pro-gated type should 404, not advertise itself with a 403.

**Nothing about CRUD changes the routing.** Creating a snippet does not need a `/items/snippets/new`
route — the drawer is UI state, not a URL. If a shareable create link is ever wanted, `?new=1` on the
existing route is the cheap version, and a parallel/intercepting route is the expensive one. Neither
is needed for Phase 2.

## 4. Zod contracts — `src/lib/item-schemas.ts`

**Proposed.** Mirrors `auth-schemas.ts`: one module, shared by every entry point that has to agree on
what a valid item is.

```ts
import { z } from "zod";
import { SYSTEM_ITEM_TYPE_NAMES } from "@/config/item-type-catalog";

const title = z.string().trim().min(1, "Give this item a title.").max(200);
const description = z.string().trim().max(500).optional();

/**
 * The item type is submitted by *name*, not id: the catalog can resolve a name to everything the
 * write path needs (contentType, isPro) without a database round trip, and the action re-resolves
 * the persisted row anyway. Custom types (Phase 7) will not be in this enum — see §11.
 */
const itemTypeName = z.enum(SYSTEM_ITEM_TYPE_NAMES as [string, ...string[]]);

/** One field for the body regardless of type. The action routes it to the right column (§5.3). */
const body = z.string().max(100_000);

export const createItemSchema = z.object({
    title,
    description,
    itemTypeName,
    body,
    language: z.string().trim().max(50).optional(),
    tags: z.array(z.string().trim().min(1).max(30)).max(10).default([]),
    collectionIds: z.array(z.string().cuid()).default([]),
});

export const updateItemSchema = createItemSchema.extend({ id: z.string().cuid() });
```

**`contentType` is deliberately absent from the input.** It is derived, never submitted — §5.3. A
form field for it would be the single easiest way to break the invariant the schema does not enforce.

Two details carried over from `auth-schemas.ts`: normalise *before* validating (`.trim()` ahead of
the check, not after — the comment at [auth-schemas.ts:9](../src/lib/auth-schemas.ts#L9) explains why
the reverse silently rejects pasted input), and keep the schema loose where strictness would reject
existing rows.

A `URL` item should additionally validate that `body` parses as a URL. Because that rule depends on
the resolved content type, it belongs in a `superRefine` keyed off `itemTypeName`, or — simpler — as
an explicit check in the action after the catalog lookup. Recommend the latter: one branch in one
place beats a conditional schema.

## 5. The write boundary

This is the substance of the design. The schema enforces almost none of it, so the action module *is*
the enforcement. Five responsibilities, in the order they must run.

### 5.1 Ownership — never from the client

```ts
const userId = await getCurrentUserId();
```

No mutation accepts a `userId` field, and no `where` clause is keyed on `id` alone. Every update and
delete is scoped by both:

```ts
await prisma.item.update({ where: { id, userId }, data });   // ← not { where: { id } }
```

This mirrors the read side, which already got it right and said why: *"Scoped by owner as well as id:
an id alone would let one user read another's collection"*
([collections.ts:141](../src/server/collections.ts#L141)). For writes the same omission is worse — it
is a cross-tenant *write*. Prisma's `update` requires a unique `where`, so `{ id, userId }` needs
`@@unique([id, userId])` on `Item` or an `updateMany` with a count check. **Recommend `updateMany` +
count check** — no migration, and a count of 0 is an unambiguous "not yours or not there".

### 5.2 Item type resolution — never `findUnique` by name

```ts
// ✗ type-checks, and is wrong
prisma.itemType.findUnique({ where: { name } });

// ✓
prisma.itemType.findFirst({ where: { name, userId: null } });
```

The partial unique index leaks `name` into `ItemTypeWhereUniqueInput` through
[prisma#29282](https://github.com/prisma/prisma/issues/29282), so the wrong call compiles. `name` is
unique only among *system* rows; a user's custom type may share it.

`getItemTypePageData` already does this correctly inline
([items.ts:92](../src/server/items.ts#L92)). The write path needs the identical lookup, which is one
copy too many — **extract `getSystemItemTypeByName(name): Promise<ItemTypeViewModel | null>` into
`src/server/item-types.ts`** and have both call it. Two hand-maintained copies of a rule whose whole
purpose is to stop a subtle bug is how the subtle bug comes back.

### 5.3 Content type — derive it, then route the body

**The most important rule in this document.** `Item.contentType` is denormalized against its
`ItemType`, and *nothing in the database enforces the agreement* — no check constraint, no trigger
(see `docs/item-types.md` §4). The seed keeps it honest by deriving rather than accepting:

```ts
// prisma/seed.ts:99 — the pattern to copy
const { contentType } = ITEM_TYPE_CATALOG[item.type];
content: contentType === "TEXT" ? item.body : null,
url:     contentType === "URL"  ? item.body : null,
```

The action does the same through one pure helper:

```ts
// src/lib/item-content.ts — pure, no server-only, unit-tested
export function toItemBody(contentType: ContentType, body: string) {
    return {
        content: contentType === "TEXT" ? body : null,
        url: contentType === "URL" ? body : null,
        fileUrl: null,      // FILE is Phase 4 — see §7
        fileName: null,
        fileSize: null,
    };
}
```

Every branch is written on every call, including the nulls. That matters on **update**: switching an
item from `link` to `note` must clear `url` as it sets `content`, or the row keeps a stale body in a
column its content type says is empty. Returning a complete object makes that automatic instead of
remembered.

The prompt asks to *validate* that `contentType` matches the catalog. Deriving is strictly stronger:
a value that is never accepted cannot be wrong, so there is nothing to validate. Accept
`itemTypeName`, look up `contentType`, done.

### 5.4 Entitlement

```ts
if (!canAccessItemType(user.isPro, itemType.isPro)) {
    return { error: "Files and images are a Pro feature." };
}
```

`canAccessItemType` already exists and already short-circuits on `ENFORCE_PRO_LIMITS`, which is
`false` during development ([lib/limits.ts](../src/lib/limits.ts)) — so this check is inert today and
becomes real when billing lands, with no code change.

**The 50-item free-tier cap is not implemented anywhere.** `limits.ts` holds only
`canAccessItemType`. Creating items is exactly where that cap has to be checked, so
`createItem` should call a new sibling:

```ts
export function canCreateItem(userIsPro: boolean, currentItemCount: number): boolean {
    return !ENFORCE_PRO_LIMITS || userIsPro || currentItemCount < FREE_ITEM_LIMIT;
}
```

Same shape, same flag, same test file. `project-overview.md` §11 lists "where limits are checked" as
an open question — this answers it for items: in the action, before the insert, on a live `count()`.

### 5.5 Validate, then write

Order matters. Ownership → parse → resolve type → entitlement → derive body → write. Parsing before
resolving avoids a database call for input that was never valid; resolving before the entitlement
check is required because `isPro` comes from the catalog via the resolved type.

## 6. The six mutations

All in `src/actions/items.ts`, all Server Actions, all following the `account.ts` signature.

| Action | Signature | Notes |
|--------|-----------|-------|
| `createItem` | `(prev, FormData) => ItemActionState` | Checks `canCreateItem`; connects tags and collections in the same `create` |
| `updateItem` | `(prev, FormData) => ItemActionState` | `updateMany({ where: { id, userId } })`; re-derives the body columns |
| `deleteItem` | `(prev, FormData) => ItemActionState` | `deleteMany({ where: { id, userId } })`; join rows cascade |
| `toggleFavorite` | `(itemId: string) => ItemActionState` | Plain arg, not FormData — one boolean, no form |
| `togglePin` | `(itemId: string) => ItemActionState` | Same |
| `setItemCollections` | `(itemId, collectionIds[]) => ItemActionState` | Replaces membership; validates every collection is the user's |

`ItemActionState` mirrors `AccountActionState` — `{ error, fields?, success? }` — and lives in
`src/types/item.ts` alongside `EMPTY_ITEM_STATE`, for the `"use server"` reason in §2.

The two toggles take a plain argument rather than `FormData` because they are buttons, not forms.
They are still Server Actions, still `"use server"`, and still re-resolve the owner — a bare item id
from the client is not authority to flip a flag on it.

### Tags

`Tag.name` is globally unique, so tags are shared rows. The seed's `connectOrCreate` is the pattern
to reuse ([seed.ts:115](../prisma/seed.ts#L115)) — it connects an existing row or creates one, and
cannot race into a duplicate. Note the known wart: tags are global, so one user's tag names pollute
another's autocomplete (`project-overview.md` §11). CRUD does not fix that and should not try; it is a
migration, not an action.

## 7. Actions or route handlers?

**All six are Server Actions. None needs to be a route handler.**

The project rule is explicit — an action when the caller needs only success or a message, a route
handler when it needs to read an HTTP status
([actions/account.ts:13](../src/actions/account.ts#L13)). Applying it:

- No item mutation has two failure modes the *client* must distinguish. "Title is required" and
  "you've hit the free limit" are both messages rendered in the same place. Contrast
  `api/auth/register`, which exists as a route precisely because the form must tell a 409 (email
  taken) from a 400 (invalid input) — a distinction that changes which field gets the error and
  whether a "sign in instead" link appears.
- No webhook, no long-running work, no third-party callback.
- No external client. `api/items/` is listed as planned in `project-overview.md` §9 for a future
  mobile/CLI consumer — a real reason for a route, but not one Phase 2 has.

**The one genuine exception is Phase 4, not Phase 2:** file and image uploads need
`api/upload/` for presigned R2 URLs — upload progress and status codes are both on the standards'
route-handler list. That is why `toItemBody` returns `fileUrl: null` today (§5.3): the FILE branch is
deliberately unbuilt, and an action cannot serve it. When it lands, the route mints the presigned URL
and the *action* still writes the row, given the resulting object key.

## 8. Reads the drawer needs

**Proposed.** One addition to `src/server/items.ts`, because list reads deliberately never load a
body:

```ts
/** Owner-scoped: an id alone would let one user read another's item. */
export async function getItemDetail(itemId: string): Promise<ItemDetailViewModel | undefined> {
    const userId = await getCurrentUserId();
    const row = await prisma.item.findFirst({ where: { id: itemId, userId }, select: { ...ITEM_DETAIL_SELECT } });
    ...
}
```

`ITEM_SUMMARY_SELECT` omits `content`, `url`, and `fileUrl` on purpose — that is what keeps list
queries off the large columns ([items.ts:13](../src/server/items.ts#L13)). The detail select adds
exactly those, plus `language` and the item's collection ids.

`ItemDetailViewModel` extends `ItemSummaryViewModel` with `body: string`, `language: string | null`,
and `collectionIds: string[]`. Flattening the three body columns into one `body` at the view-model
boundary is consistent with everything else in `view-models.ts` — the UI should no more branch on
which column was populated than it should know `description` was nullable.

## 9. Components

### Drawer — `ItemDrawer.tsx`

`project-overview.md` §8 specifies a slide-out drawer for view / edit / create. **There is already a
slide-out drawer in this codebase**, and it is not a shadcn `sheet`: `Sidebar.tsx` uses `Dialog` from
the unified `radix-ui` package directly — `Root` / `Portal` / `Overlay` / `Content` with `sr-only`
`Title` and `Description` ([Sidebar.tsx:29](../src/components/layout/Sidebar.tsx#L29)). Follow that
rather than installing a new primitive. `radix-ui@1.6.2` is already a dependency; `src/components/ui`
has no `sheet.tsx` and does not need one.

The drawer is a client component holding `mode` (`view | edit | create`) and the open item's id. It
fetches nothing itself — the server component passes the detail view model in, or the trigger passes
the id and a server action returns it.

### Form — `ItemForm.tsx`

One form for all seven types, `useActionState` + `FormData`, no `react-hook-form` (not a dependency,
and the four existing forms do without it). Copy `ChangePasswordForm` verbatim in structure:
`aria-invalid` / `aria-describedby` wired to `state.fields`, a `role="alert"` block for
`state.error`, a `useEffect` on `state.success` that resets the form and raises a toast
([ChangePasswordForm.tsx:28](../src/components/profile/ChangePasswordForm.tsx#L28)).

Fields shared by every type: title, description, tags, collections. Then one branch.

### Body editor — `ItemBodyEditor.tsx`

The single point of type-specific presentation, switched on `contentType` from the catalog — **not**
on the type name. Four TEXT types share one editor; adding an eighth TEXT type needs no change here.

| `contentType` | Editor |
|---------------|--------|
| `TEXT` | Monospace `<textarea>`; a `language` select for `snippet` / `command` |
| `URL` | Single `<input type="url">` |
| `FILE` | Upload control — **Phase 4**; render a disabled placeholder until `api/upload/` exists |

Markdown editing and syntax highlighting are listed in §4E/§8 but have **no dependency installed**
(no editor, no highlighter). A plain monospace textarea is the honest Phase 2 scope; the editor is a
later swap behind this one component.

### `ItemCard` and `TypeIcon` — reuse, do not fork

`ItemCard` already renders every type correctly, driven entirely by `item.itemType.color` and
`.icon`. It needs exactly one change: become a drawer trigger. It is currently a plain `<article>`
with no interactivity, so it stays a server component and the *trigger* wrapper is the client
boundary — the same shape `CollectionCard` uses with its `Link`.

`TypeIcon` needs no change at all. Its exhaustive `switch` with `assertNever` means a new icon is a
compile error, which is the behaviour you want.

## 10. Revalidation

**There is no `revalidatePath` call anywhere in the codebase today** — nothing has mutated shared
state before. Two facts shape the design:

1. `export const dynamic = "force-dynamic"` on the dashboard layout
   ([layout.tsx:12](../src/app/(dashboard)/layout.tsx#L12)) applies to every child segment, so
   nothing under `(dashboard)` is prerendered or served from a full-route cache.
2. Next's **client-side Router Cache** still holds RSC payloads for already-visited routes. So a
   mutation that changes another route's content still needs an explicit invalidation, even though
   the server would happily re-render.

What every item mutation touches:

| Surface | Why it changes |
|---------|----------------|
| `/` | Item totals, favourite count, pinned list, recent list |
| `/items/[slug]` | The type's own list and its count |
| `/collections/[id]` | Membership, and possibly the dominant-type accent |
| `/collections` | Same, for every card |
| Sidebar (in the layout) | Per-type counts, collection dots |

**Recommendation: `revalidatePath("/", "layout")` — one call, from every item mutation.**

The fine-grained alternative is real but false economy here. *Every* item mutation changes a sidebar
count, and the sidebar lives in the layout, so every mutation invalidates the layout anyway — at
which point enumerating `/items/snippets` and three collection ids buys nothing and adds a way to be
wrong. Update is the clearest case: changing an item's type must invalidate **both** the old and new
slug pages, and the fine-grained version has to remember that.

Where fine-grained does pay: `toggleFavorite` and `togglePin` fire often and from list views, and a
full layout invalidation on every star click is heavy. Those two are the candidates for
`revalidatePath("/")` plus the one type page — or for optimistic client state with no revalidation
at all.

## 11. Open questions

1. **Item type by name or by id?** This design submits `itemTypeName`, which the catalog resolves
   without a query. Custom types (Phase 7) will not be in `SYSTEM_ITEM_TYPE_NAMES`, so the `z.enum`
   breaks the moment they ship. Submitting `itemTypeId` and resolving via
   `{ OR: [{ userId: null }, { userId }] }` — which `getItemTypesById` already does — survives that
   change. Name is simpler now; id is the one that lasts. Worth deciding before writing the form,
   because it is the field name in the DOM.
2. **The free-tier item cap.** `canCreateItem` is proposed above but `FREE_ITEM_LIMIT` has no home
   yet — `config/access.ts` is the obvious one, beside `ENFORCE_PRO_LIMITS`. Also: hard block, or
   create-then-prompt? §11 of the overview leaves it open.
3. **Soft delete.** `deleteItem` as designed is irreversible; there is no `deletedAt`. If a trash
   view is ever wanted it is a migration, and it is cheaper to decide now than to add a column to a
   populated table later.
4. **Tag scoping.** Global tags leak across users. Not CRUD's problem to fix, but CRUD is what makes
   the leak visible, since it is the first feature that lets a user create a tag.

## 12. Testing

The repo has ten unit test files and the standards ask for "focused unit tests for non-trivial
business rules and data transformations". The three testable-in-isolation pieces here:

| Module | What to assert |
|--------|----------------|
| `lib/item-content.ts` | Each content type populates exactly one column and nulls the rest; a type switch clears the old column |
| `lib/item-schemas.ts` | Trim-before-validate; the max bounds; tag array limits — mirrors `auth-schemas.test.ts` |
| `lib/limits.ts` | `canCreateItem` at the boundary (49 / 50 / 51), Pro bypass, flag-off bypass |

The actions themselves are integration surface — they need a database — and the existing suite does
not cover `actions/account.ts` either. Browser verification is warranted here per
`ai-interaction.md`: item CRUD through the real UI is explicitly on the end-to-end list.
