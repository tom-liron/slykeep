# Item Types

Reference for DevStash's seven system item types: what each one is, what it persists, and how it
renders.

Generated by `/research context/research/item-types-research.md`. Documentation only — it describes
the code as it stands, and is not itself authoritative. When this disagrees with
`config/item-type-catalog.ts` or `prisma/schema.prisma`, those win.

---

## 1. Where an item type's data lives

An item type is assembled from **two sources**, and neither is complete on its own:

| Source | Owns | Fields |
|--------|------|--------|
| **Database** — `item_types` table | Identity | `id`, `name`, `icon`, `color`, `isSystem`, `userId` |
| **Config** — `src/config/item-type-catalog.ts` | Presentation & gating | `label`, `slug`, `contentType`, `isPro` (plus the `icon` and `color` the seed writes) |

`name` is the natural key that joins them — lowercase singular (`snippet`, `prompt`, …). The join
happens at the server boundary, in `toItemTypeViewModel()`
([src/server/view-models.ts:94](../src/server/view-models.ts#L94)), which produces the
`ItemTypeViewModel` every component consumes. No component ever sees a Prisma `ItemType` row.

Two consequences worth internalising:

- **Adding a display field does not need a migration.** Label, route, content type, and Pro gating
  are code. Only `icon` and `color` round-trip through the database, and only because the seed puts
  them there.
- **`name` and `icon` are untyped `String` columns.** They are validated in `toItemTypeViewModel`
  via `isItemTypeName()` and `isIconName()`, which **throw** rather than fall back. An unknown type
  name or an unsupported icon fails the request loudly; there is no default type.

This split is a deliberate divergence from the course, which puts everything on the model. See the
Course Mapping table in `CLAUDE.md`, and `context/project-overview.md` §5.

## 3. Per-type detail

Every type shares the same `Item` row shape (§5); what differs is which body column it populates and
what the type is *for*.

### 1. Snippet — `#3b82f6`, `Code`, TEXT

Reusable code. The most field-heavy type in practice: `content` holds the code, and `language` is
set for syntax highlighting.

- **Populates:** `content`, `language`
- **Seed examples:** `useDebounce`, `createSafeContext`, `groupBy` (all `typescript`), a multi-stage
  `Dockerfile` (`dockerfile`)
- **Notes:** the only type besides `command` that the seed gives a `language`.

### 2. Prompt — `#8b5cf6`, `Sparkles`, TEXT

Saved AI prompts and system messages — one of the product's two named differentiators (the AI-first
developer in `project-overview.md` §2).

- **Populates:** `content`
- **Seed examples:** "Code review", "Generate documentation", "Refactoring assistance" — each with
  `{{placeholder}}` interpolation markers
- **Notes:** no `language`; prompts are prose, not code. The Pro "prompt optimizer" (Phase 5) will
  operate on this type.

### 3. Command — `#f97316`, `Terminal`, TEXT

Shell commands and one-liners worth not re-deriving.

- **Populates:** `content`, `language` (`bash` throughout the seed)
- **Seed examples:** `git reset --soft HEAD~1`, Docker prune, find-and-kill-a-port, `npm outdated`
- **Notes:** structurally identical to `snippet` — same content type, same columns. The distinction
  is organisational, not technical: it buys a separate route, color, and count.

### 4. Note — `#fde047`, `StickyNote`, TEXT

Free-form Markdown notes and explanations.

- **Populates:** `content`
- **Seed examples:** *none* — no seeded item uses this type.
- **Notes:** its sidebar row and `/items/notes` page render with a count of zero and an
  `EmptyState`, which is exactly what the `?? 0` in `getItemTypeCounts` exists to guarantee (§6).

### 5. File — `#6b7280`, `File`, FILE — **Pro**

Uploaded files: context files, templates, documents.

- **Populates:** `fileKey`, `fileName`, `fileSize` (Cloudflare R2 object)
- **Seed examples:** *none.*
- **Status:** **shipped.** `POST /api/upload` authorizes the request and puts the object itself, so
  the browser never talks to R2; `GET /api/files/[id]` streams it back, authorized per request. The
  column is `fileKey` rather than `fileUrl` — migration `20260806081153_rename_file_url_to_file_key`
  — because what is stored is an object key, never a URL: a URL would either be public or expire,
  and both are decisions the route should make per request.

### 6. Image — `#ec4899`, `Image`, FILE — **Pro**

Screenshots and diagrams. Identical persistence to `file`; separated for its own route, color, and
eventual thumbnail rendering.

- **Populates:** `fileKey`, `fileName`, `fileSize`
- **Seed examples:** *none.*
- **Status:** same as `file` — schema only.

### 7. Link — `#10b981`, `Link`, URL

Bookmarked references and documentation.

- **Populates:** `url`
- **Seed examples:** Docker best practices, GitHub Actions syntax, Tailwind docs, shadcn/ui,
  Material Design 3, Lucide icons
- **Notes:** the only `URL` type, and therefore the only one whose body is a single short string.

### Seeded distribution

`prisma/seed-data.ts`, 18 items across 5 collections:

| Type | Items | | Type | Items |
|------|-------|-|------|-------|
| link | 6 | | note | 0 |
| command | 5 | | file | 0 |
| snippet | 4 | | image | 0 |
| prompt | 3 | | **Total** | **18** |

The three empty types are the useful test case: they exercise the zero-count path in the sidebar and
the `EmptyState` on their type pages.

## 4. TEXT vs FILE vs URL

`ContentType` is a persisted Postgres enum (`schema.prisma:93`) with three members. It sits on
**`Item`**, not on `ItemType` — it is a property of the stored content, and its job is to
**discriminate which body column is populated**:

| `ContentType` | Types | Body column(s) | Shape |
|---------------|-------|----------------|-------|
| `TEXT` | snippet, prompt, command, note | `content` | Arbitrarily long text; may carry `language` |
| `URL` | link | `url` | One short string |
| `FILE` | file, image | `fileUrl`, `fileName`, `fileSize` | R2 object pointer + metadata |

Four TEXT, two FILE, one URL. Both FILE types are Pro-gated; nothing else is — so Pro gating and
`FILE` are currently the same partition, though the catalog treats them as independent flags.

### The denormalisation, and what keeps it honest

`Item.contentType` is redundant against `Item.itemType.contentType` — a snippet is *always* `TEXT`.
The schema does **not** enforce the agreement; there is no check constraint and no trigger. It is
enforced at the write boundary instead, by deriving rather than accepting the value:

```ts
// prisma/seed.ts:99 — derived, never hand-written
const { contentType } = ITEM_TYPE_CATALOG[item.type];

content: contentType === "TEXT" ? item.body : null,
url:     contentType === "URL"  ? item.body : null,
```

The seed takes one `body` string and routes it to the correct column, so a mismatch is
unrepresentable rather than merely discouraged. **Item CRUD is roadmap Phase 2 and does not exist
yet** — when Server Actions land, they must derive `contentType` the same way. This is the single
easiest invariant in the codebase to break, because breaking it requires only that someone accept
`contentType` from a form.

## 5. Properties every type shares

All seven types are the same `items` row ([schema.prisma:123](../prisma/schema.prisma#L123)). There is
no per-type table and no subtyping.

| Field | Type | Notes |
|-------|------|-------|
| `id` | `String` | cuid |
| `title` | `String` | Required, the only required body-ish field |
| `contentType` | `ContentType` | Discriminator — see §4 |
| `content` / `url` / `fileKey` / `fileName` / `fileSize` | nullable | Exactly one branch populated |
| `description` | `String?` | Normalised to `""` in the view model |
| `language` | `String?` | Free text; `lib/code-language.ts` maps it to a monaco language id, and `CodeEditor` highlights with it |
| `isFavorite` | `Boolean` | Default `false` |
| `isPinned` | `Boolean` | Default `false` |
| `userId` | FK → `users` | `onDelete: Cascade` |
| `itemTypeId` | FK → `item_types` | No cascade — types are reference data |
| `tags` | `Tag[]` | Implicit m-n, `ItemTags` |
| `collections` | `ItemCollection[]` | Explicit m-n join carrying `addedAt` |
| `createdAt` / `updatedAt` | `DateTime` | `updatedAt` drives all recency ordering |

Indexed on `userId`, `itemTypeId`, and `createdAt`.

So **favouriting, pinning, tagging, collection membership, and search all work identically across
types** — none of them branches on the type. A type is a label, a color, a route, and a content
discriminator; it is not a behaviour.

## 6. Display differences

The type drives **color and icon**, and nothing else. Every surface applies those two the same way.

| Surface | How the type shows up |
|---------|----------------------|
| [ItemCard](../src/components/items/ItemCard.tsx) | 4px left border in `itemType.color`; icon tile using `withAlpha(accent)` (10% alpha) as background and the full color as foreground |
| [Item type page](../src/app/(dashboard)/items/[slug]/page.tsx) | Header icon tinted with the type color, `label` as `<h1>`, item count, then a flat `ItemCard` list |
| [SidebarNav](../src/components/layout/SidebarNav.tsx) | One row per type: tinted `TypeIcon`, `label`, live item count, linking to `/items/${slug}` |
| [CollectionCard](../src/components/collections/CollectionCard.tsx) | Left border in the **dominant** type's color; a footer row of tinted icons, one per contained type |
| Sidebar collection dot | Solid dot in the dominant type's color, titled `Mostly {label}`; a hollow bordered dot when there is none |
| Profile page | Per-type breakdown via the shared `getItemTypeCounts` |

Colors are applied as **inline `style`**, not Tailwind classes — deliberate, per
`coding-standards.md`: the values are runtime data (a custom type will bring its own), and Tailwind
cannot generate a class for a hex it never saw at build time.

**What does *not* differ today.** There is no per-type card layout, no type-specific body rendering,
no syntax highlighting (`language` is stored and ignored), no image thumbnails, and no link preview.
A link and a snippet render identically bar the color and icon — because list views never load a
body at all (§7). Type-specific rendering arrives with the item drawer in Phase 2.

### Dominant type

A collection's accent comes from its dominant type
([view-models.ts:141](../src/server/view-models.ts#L141)):

1. The most common item type among the collection's items.
2. Ties break toward the type of the **most recently updated** tied item.
3. Empty collection → fall back to `defaultTypeId`.
4. Empty *and* no default → `null`, and the card renders a neutral accent.

## 7. Reads, counts, and access

**List queries never select a body.** `ITEM_SUMMARY_SELECT`
([items.ts:34](../src/server/items.ts#L34)) omits `content`, `url`, and `fileUrl`, keeping list reads
off the large columns. Detail reads select them only where the drawer needs them.

**Counting includes empty types.** `getItemTypeCounts` uses a single `groupBy` plus `?? 0`
([item-types.ts:85](../src/server/item-types.ts#L85)) — `groupBy` emits no row for an empty group, so
without the fallback the zero-item types (note, file, image) would vanish from the sidebar and the
profile breakdown rather than read `0`.

**Pro gating is on.** `canAccessItemType(userIsPro, itemTypeIsPro)` short-circuits on
`ENFORCE_PRO_LIMITS`, which is now `true`
([config/access.ts](../src/config/access.ts)) — it was flipped once billing state became
authoritative, so an account that is not Pro is a fact about what was paid for rather than an
artefact of an unfinished integration. For a free account `file` and `image` are absent from the
sidebar and their routes 404 via `getItemTypePageData` returning `undefined`, and the same switch
also enforces the free tier's item and collection caps (`lib/limits.ts`).

## 8. Invariants and gotchas

1. **Never `findUnique` an item type by `name` alone.** A [Prisma bug](https://github.com/prisma/prisma/issues/29282)
   leaks `name` into `ItemTypeWhereUniqueInput` because of the partial index, so it type-checks — but
   `name` is unique only among *system* rows, and a user's custom type may share it. Use
   `findFirst({ where: { name, userId: null } })`, as `getItemTypePageData` does.
2. **`@@unique([name, userId])` does not constrain system types.** Their `userId` is `NULL`, and
   Postgres treats every `NULL` as distinct, so `('snippet', NULL)` could be inserted repeatedly. The
   partial index `@@unique([name], where: { userId: null })` closes it. It is declared in the schema,
   not hand-written in SQL, because since 7.4 Prisma emits a `DROP` for database objects it cannot
   see in the schema.
3. **The seed reads-then-writes instead of upserting** — for the same `NULL` reason: an upsert
   matching on `[name, userId]` would never hit for a system type and would insert a duplicate set on
   every run.
4. **`npm run db:seed:types` (`--types-only`) is the only part safe against production.** Item types
   are reference data every `Item` FKs into; the demo user's password lives in a committed file.
5. **Unknown types fail loudly.** `toItemTypeViewModel` throws on an unrecognised `name` or `icon`,
   and `requireItemType` throws on an unresolvable `itemTypeId`. Fallbacks were deliberately removed
   (feature-history #7).
6. **Custom types are Pro and unbuilt.** The schema supports them (`userId`, `isSystem`), and
   `getItemTypesById` already returns `{ userId: null } OR { userId }`. But `isItemTypeName()` gates
   on the catalog, so a custom type would throw at the view-model boundary today. Roadmap Phase 7.
7. **Tags are global, not per-user** (`Tag.name @unique`) — a known open question in
   `project-overview.md` §11, deferred to keep the migration path aligned with the course.

**Verification note.** Everything above was read from source. The seeded `item_types` rows in the
Neon development branch were **not** queried, so the persisted `icon`/`color` values are documented
as what `prisma/seed.ts` writes from the catalog, not as what the database currently holds. The seed
is authoritative by construction — it updates `icon` and `color` on every run — but a row edited by
hand since the last seed would not be reflected here.
